# 64-job 写事务分阶段诊断

**结果：秒级尾延迟主要发生在实际写锁获取阶段；全池库存校验又占持锁业务时间的约三分之二。需要同时处理公平准入和事务影响范围，不能只增加线程，也不能只上 FIFO 后再盲跑正式负载。**

本目录是有边界的机制诊断，不是性能验收。生产源码与 HEAD 保持 `b19acae7f0ea185e6289388fb629d2a15dd84fad`，source SHA256 为 `68297acee1ac17e34d6735d724bda124814afd17c62d8857f971fb1d2fa3d6f9`。第一次工具启动失败、唯一一次修复后重试及完整原始输出均保留。

## 1. 方法与固定边界

预先声明 64 jobs、两波各32流程、320写请求和8次 job-detail 查询。直接复用冻结 `_load_runner.Load` 的库存、流程、请求体、客户端和窗口，保留128节点、1,024物理GPU、64 Owner、真实TCP、4 vCPU/8 GiB约束、原生容器磁盘和SQLite WAL/FULL。不修改产品源代码，不调整客户端并发或超时，不重跑完整负载。

诊断 wrapper 仅在独立服务进程内装饰既有调用边界，使用 `perf_counter_ns`：

- 在真正 `connection.execute("BEGIN IMMEDIATE")` 调用前后取时，得到**写锁获取耗时**；这包含这条SQL调用本身的少量开销，不是假定的纯睡眠时间。
- 在取得写锁后、事务业务体前后，以及真正 `connection.commit()` 前后取时，得到持锁业务和 durable COMMIT。持锁区间从 BEGIN 返回到 COMMIT 返回。
- 在 `_inventory`、`save`、`changed_units` 边界取时。`changed_units` 包含在 `save` 中；二者不能再次相加。库存校验和保存是业务体中的不重叠阶段。
- 在线程池 await 前、工作函数实际进入、工作函数完成和 await 返回时取时，分开线程准入及结果交付延迟。
- 通过请求 ContextVar 将上述记录与真实 `X-Request-Id` 关联。启动、健康检查和后台只读记录不冒充业务事务。
- 所有事件先保存在进程内存，服务 lifespan 正常关闭后一次性写盘，没有逐事务日志磁盘写入。

计时装饰、连接代理和事件收集仍有开销。因此这些数值用于归因和设计预算，不作为无侵入吞吐结果；没有用host单请求延迟作减法猜测锁等待。

## 2. 首次失败必须保留

首次计划运行没有完成健康检查，实际执行 **0 jobs、0业务请求**。当时外层冻结runner将启动错误收进metadata并返回，进程退出码为0，不等于诊断成功。状态为 `DIAGNOSTIC_FAILED` / 业务 `NOT_RUN`。

原因是诊断 wrapper 的线程池函数将首个参数命名为 `function`，与FastAPI转发给工作函数的同名关键字冲突：

```text
TypeError: install.<locals>.timed_pool() got multiple values for argument 'function'
Isolated product host did not start
```

已保留：

- [首次状态](first-attempt-status.json)、[首次执行日志](execution.log)。
- [首次完整run目录](run-b19acae-64/)，包括约7.1 MiB的原始server.log，Git内以[无损gzip](run-b19acae-64/server.log.gz)保留；解压后的原件SHA见[保留记录](run-b19acae-64/server-log-preservation.json)。
- [失败版本wrapper](phase_service.failed-v1.py)、[失败版本driver](run_diagnostic.failed-v1.py)、[首次事件](service-events.json)。

随后只修复工具签名为位置专用 `func`，先做不启动app/数据库/负载的关键字转发适配检查，见 [wrapper-preflight.log](wrapper-preflight.log)。经重新声明后仅重试一次相同64-job诊断；改用全新输出和 `/tmp/fabric-phases-b19acae-64-20261115-retry1`，首次数据未覆盖。driver也改为核验实际64完成及无错误后才返回成功。未从首次启动事件推导任何业务性能结论。

以下为320次业务写；线程池列为656次线程分派。详细数据见 [summary.json](summary.json)、[逐事务结果](transactions.json)。

| **实际 BEGIN 获取** | **553.43** | **0.015** | **3,756.75** | **5,189.17** |
| **持锁总服务（含COMMIT）** | **26.06** | **22.89** | **43.94** | **104.27** |
| 持锁业务体 | 24.27 | 21.27 | 43.03 | 101.96 |

实际BEGIN获取时间之和占客户端写请求时间之和的 **92.53%**。这两个和是逐请求分量的对照；不同请求的等待相互重叠，177.10秒累计等待绝不能当作10.81秒运行中额外经过的墙钟时间。不同阶段的p95也不能相加。

**线程池排队、结果交付和 durable COMMIT 都没有秒级尾部。** 本样本明确支持写锁竞争是秒级延迟的直接位置，未发现“都花在fsync”或“线程池排队数秒”的证据。

## 5. 公平性与空隙

比较实际BEGIN调用开始顺序与成功取得锁的顺序，共出现4,388对次序倒置。最长等待请求 `cp4-load-189` 为allocation：等待5.189 s期间，有 **141个更晚开始获取锁的事务先获得锁**。其他长尾请求也被后到事务越过100次以上。这里比较的是服务内真实锁边界，不再仅凭客户端响应顺序猜测。

首次取得锁至最后COMMIT完成的跨度10.780 s，总持锁8.339 s，写者占用比77.36%。319个相邻持锁区间之间空隙累计2.441 s，p95约34.94 ms、最大95.14 ms；其中311个空隙发生时，已有事务发起BEGIN但尚未取得锁，合计2.346 s。见 [writer-gaps.json](writer-gaps.json)。

该现象支持用本进程FIFO/有界准入避免大量线程同时在SQLite busy等待并减少后到越过；它不是SQLite内部busy算法的直接追踪。记录时刻位于函数返回侧，OS线程调度也可形成部分空隙，因此不能将所有2.346 s精确归给某个SQLite退避常数。

## 6. 下一阶段选择：公平准入与资源局部化分别负责什么

**公平准入处理已测到的饥饿和锁争抢，资源局部化处理串行服务预算；两者不能互相替代。**

1. 本进程有界FIFO事务准入是针对长尾越过的直接结构修复。它必须在finally中释放，异常不堵后继，普通只读快照不排入写队列；SQLite BEGIN IMMEDIATE继续承担跨进程正确性。不能因此宣称跨进程全局公平，也不增加无限工作线程。
2. 达标核心仍需要缩小事务校验作用域，并区分只读实体与真正脏实体。每次写都重建128节点库存及编码这批只读节点，已成为明确的固定成本。应按变更影响的节点/设备/声明复核资源守恒，并保留完整审计作为独立对照；不移除原子硬约束校验。新申请、释放、恢复、贡献者回收、节点故障、到期、reset及旧代次隔离都不能漏进影响集。
3. 不能只完成FIFO就再次跑完整负载。以本样本mean26.06 ms粗略估算，单写者持续忙碌也只有约38.4写/s；50,000写/1,200 s要求平均持锁服务低于24 ms，且还有其他开销。32请求公平队列在26 ms服务时间下仍是约0.8秒量级，而冻结门槛是各普通操作p95<200 ms；单写者的服务预算要接近6 ms量级才能为这类突发留出空间。这是容量推算，不是严格下界证明。
4. 即使理想化把16.12 ms库存成本全省掉，仍剩约9.93 ms/写；所以只改变库存计算而让128只读节点继续进入变化编码，也可能不足。`changed_units`另有3.94 ms，但包含其他实体，不能把它全部归为节点或承诺全部省掉。

后续应先用与本次相同边界的小样本核验“越过是否消失、持锁时间是否显著缩短、资源守恒与完整重放是否不变”，再决定是否冻结一次正式候选。没有扩大诊断规模，没有继续调整策略评分，没有得出“无法继续优化”的结论。
