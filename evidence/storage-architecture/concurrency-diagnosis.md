## 2. 已从源码确认的阻塞路径

### 2.1 未启用故障注入，也在事件循环里获取写锁

调用链如下：

```
app.py::correlation（async middleware，事件循环）
  -> await intercept_fault(...)
     -> faults.py::intercept_fault
        -> kernel.take_fault(target)（同步调用）
           -> lifecycle.py::take_fault
              -> SQLiteStore.transaction()
                 -> BEGIN IMMEDIATE
              -> load roots + inspect faults[target]
              -> 无规则时直接返回，随后提交/关闭事务
  -> call_next(request)
```

源码位置：`src/campus_fabric/app.py:104` 附近，`api/test_control/faults.py:43–54`，`domain/lifecycle.py:143–152`，`storage/sqlite.py:274–295`。

`take_fault` 在判断规则存在与否**之前**已取得 `BEGIN IMMEDIATE` 写事务。所有匹配公共 API 的请求都经过这条路径，包含本轮 job-detail GET。即使测试没有配置任何 fault，普通写请求仍有“故障检查写事务 + 真正业务写事务”两次独立的写锁获取；普通 GET 也先成为一个写锁竞争者。

当工作线程正在提交业务事务时，主事件循环会同步等候 `BEGIN IMMEDIATE`。这段时间它不能继续接收/分派其他协程，也不能及时把已完成线程结果送回客户端。SQLite 的 `busy_timeout=30000` 是等待上限，**不是异步等待机制**。把业务端点移到线程池没有消除这条中间件路径。

首 5,000 响应包含 4,879 次写和 121 次 GET；按冻结代码路径，至少对应这 5,000 次故障检查事务及 4,879 次业务事务（未计当时尚未返回的请求）。次数是代码推导，未对运行进程做追踪。

现有 `tests/concurrency/test_http_event_loop.py` 未覆盖此缺陷：它在 `commit_with_payload` **尚未取得数据库写锁前**用 Event 阻塞，且探针 URL `/test-loop-probe` 不属于 fault 的公共路由集合。该测试有效验证了业务入口线程池化，但不能证明“真实持锁 + 新公共请求”时事件循环仍可运行。

### 2.2 真正业务事务仍是一个包含大量 Python 工作的全局临界区

`Kernel.commit_with_payload` 在取得写锁后才开始 `load`、授权/幂等/版本检查、执行命令、调度、构造 receipt、验证、资源守恒检查、编码变化、更新 Merkle 树与 journal；最终 `conn.commit()` 后才释放锁。

该范围是 `domain/kernel.py:252–330` 与 `storage/sqlite.py:284–295,327–392`。所以 32 个 HTTP 工作线程并不意味着 32 个内核命令并行执行。多个进程使用同一 SQLite 文件也仍受这个写事务边界约束。

剩余固定/活动规模成本包括：

- 每个业务写都会调用 `_inventory`，解析 128 个节点及 1,024 个设备，并重建资源视图；只续租也执行这项工作。
- allocation 请求先调度选位，随后最终资源校验又导出一次库存。单次请求成本还随当前活跃声明数变化；本轮可有 32 个活跃流程，与只有一个活跃声明的 host probe 不等价。
- 读取进入 LazyMap cache 的节点仍会在 `changed_units` 中编码以检测嵌套修改。最近的修补已取消 primitive 往返和 rebase 二次编码，但没有让只读节点免于第一次变化比较。
- Merkle 更新、每个实体的查询索引维护、journal 写入以及 FULL durable commit 都仍在同一临界区。具体耗时比例尚未在这个容器并发运行中分解。

源码证据：`domain/lifecycle.py:45–57`，`domain/placement.py:52–132`，`domain/kernel.py:586–611,660–678`，`storage/state.py::LazyMap.changed_units`，`storage/sqlite.py::_save_changes`，`storage/merkle.py::_put`。

## 3. 哪些解释目前不成立，哪些仍未测

| 候选原因 | 当前证据 | 可证伪方式（负载结束后、小规模诊断） |
| --- | --- | --- |
| 事件循环等待故障检查写锁 | 调用链已确认；GET 也出现秒级尾延迟，与轻量实体查询本身不相称 | 真实持有 SQLite 写事务，再并发发公共请求与独立 async probe；观察 probe 是否在持锁期间仍能完成。然后只隔离该路径做同环境有界对照 |
| 业务写事务串行服务时间过长 | 全部核心工作都在 BEGIN IMMEDIATE 到 commit 之间 | 记录 BEGIN 前后、业务 apply、inventory、changes、journal/树、COMMIT 前后时间；将锁等待与持锁服务时间分开 |
| 锁竞争缺乏公平准入，导致后到请求越过 | 没有应用层 FIFO；响应顺序存在强烈越过，但无法区分锁与响应积压 | 在事件循环不再阻塞的前提下，记录 enqueue/acquire/commit 序号及等待时间；比较有限 FIFO 准入对尾部的影响 |
| CPU driver 与后台 worker 持续争抢写锁 | 本轮 `logical_simulation`，CPU driver 不启动；只走 direct allocation/job，不注册 WorkIntent；`builtin` 模式下 WorkflowWorker 无外置策略 | 冻结配置和流程已足以排除其为本轮主要写竞争来源。worker 仍每 0.5 s 做一次轻量只读发现，影响未分解 |
| HTTP 409/重试风暴 | 冻结客户端没有重试循环，前缀 0 错误且 request ID 唯一；无 expected_version 竞态重试 | 最终原始历史核查全部请求/状态，不能只分析成功样本 |
| 线程池只有几个线程，或需要无限扩线程 | 公共同步路由/业务线程调用走 Starlette/AnyIO；当前安装版本默认 limiter 40，本轮32个客户端流程；工作流用另一个 asyncio线程执行通道 | 真正需要测的是线程排队时间与同时等待写锁数；增加线程不能解除数据库单写者或事件循环阻塞 |
| 4 vCPU 或 8 GiB 资源耗尽 | 只读 cgroup 样本无 throttling，内存约 281 MiB | 同一短诊断窗口前后取 CPU/I/O/pressure 差值；目前未测持锁 CPU/IO 分摊 |
| FULL fsync/SQLite checkpoint 是主因 | 有持久化成本，但未计时；原生容器磁盘且 pressure 样本无异常不足以排除它 | 拆出 COMMIT 耗时及 checkpoint 边界，保持 FULL，不通过减弱持久化来“通过” |
| 调度策略优化方法没有任何可能的提升 | 本轮是控制面 HTTP 生命周期负载，builtin first-fit，不测 CP3 策略收益 | 将控制面吞吐与策略 R 比值分开；本轮不能用来证明策略最优或不可优化 |

同源码指纹的 host probe（`probe/result-after-copy-fix.json`）约 21 ms 单写只提供机制背景：它在 macOS、低并发、较少活跃声明下运行，不是这个 Linux 4 vCPU 容器的服务时间基准。不能用“1,182 ms − 21 ms”伪算锁等待。客户端总延迟至少混合了分派、故障检查、线程准入、业务锁等待、持锁服务、提交以及响应分派；目前没有内部阶段时间戳。

## 4. 下一阶段的结构性选择与停止条件

建议按可判别顺序推进，**不改变正在运行的候选**：

1. **先修复请求准入与事件循环边界。** 所有可能等待 SQLite 的检查离开事件循环。对未启用 fault 的路径采用一致性只读检查；若发现可消费规则，再进入写事务重新检查并原子扣减。跨进程不缓存“没有规则”。无规则请求可在线性化的只读观察点返回，规则消费仍只能由写事务确认。保留并发 fault count、授权、崩溃恢复语义。这是公共请求执行模型修正，不能用关闭故障功能绕过。
2. **用有限的阶段计时判断下一刀落在哪里。** 保持冻结负载不变，后续只做短而能区分原因的诊断：同一容器、同样库存与活跃规模，区分线程排队/写锁等待/持锁计算/COMMIT。若修复事件循环后服务时间已满足预算但 p95 仍被越过拉长，优先研究有界 FIFO 命令准入。FIFO 能减少饥饿和锁争抢，不会凭空提升单写者的服务能力。
3. **若持锁计算仍占主导，改资源校验的作用域。** 将变更声明关联到受影响节点，事务内校验受影响的 CPU/内存/存储/GPU 父子设备与重叠声明；保留启动/离线完整资源重建作独立校验。只续租等没有资源增减的操作应有明确的安全证明，而不是依赖每次重建全池。新增请求、释放、恢复、回收、节点故障、reset、retired quarantine 都要进入影响集；禁止直接跳过守恒校验。
4. **仅在服务时间分解证明持久化是主因后考虑更大存储设计。** 可评估不改变每条命令 receipt/线性化/完整 journal 的短批次提交，或按资源节点进行事务锁的关系数据库方案。不能只把 SQLite 换成 PostgreSQL 却仍保留全局 revision/库存校验的大临界区；那会把同一个串行瓶颈迁移过去。任何分片/批次方案必须先明确跨节点声明、命令顺序、崩溃边界、幂等重放的语义。

不得以增大超时、减少32并发、缩小节点/历史规模、删除慢样本、减少查询、关闭 FULL 持久化或多开工作进程作为验收修复。本轮先完整保留最终结果。只有下阶段有界诊断已表明某个结构改变能够达到预算，才值得再次冻结候选并跑一次正式负载。

**停止条件不是“仍慢所以不能优化”。** 若阶段计时证明满足既定语义所需的不可并行持锁服务时间已大于目标预算，才可以形成带适用范围的容量边界；还需说明为什么缩小校验影响集、公平准入或改变事务组织不能改善该边界。本次尚未达到这种证明，已确认缺陷仍未修复。
