## 2. 现有证据究竟支持什么

### 2.1 两种“性能”不能混在一起

策略 R=1.00 反映固定逻辑工作量模型中的完成历时面积；HTTP 延迟反映控制面处理历史累积状态和并发请求的耗时。算法收益为零，不等于整个服务没有用户价值；控制面很慢，也不证明策略不存在改进空间。二者的修复、停止条件和比较对象不同。

只读重新打开了 125 份历史 summary，各份摘要均匹配当前证据索引，输入字节摘要也一致。独立按所有 32 项工作的完成时刻或观察窗 H 计算 F，25 个 P/B2 配对均精确为 1，完成数也逐对相同；不是 UI 舍入。历史来源仍为 `1cc2ab678570b0097e98875ad8a4d63fe296a832`，不能把它改标为 059 的新策略实验。算式、逐对结果与范围记在 `readonly-recalculation.json`。

现有诊断有机制解释：P 只能在 B2 已选工作内部改放置，790 个选中动作只有 3 次改变 B2 选择；统一 10 秒工期使型号交换常常没有结果差异。工作选择原型在小例子存在改善，但有收回场景使一个 Owner 服务从 1 降为 0。原材料与局部容量证明见 `docs/research/CP3_BOTTLENECK_AND_DIRECTION.md:9–24,54–71`。这支持停止该放置代理的微调，不支持“所有合法在线策略均无收益”。存在收益反例本身已经反驳这种全局不可优化表述。

历史实验的比较在声明模型内有配对与强基线，但不是完整现实效果证据：32 工作／run，全部同一工期；恢复成本组件未启用；逻辑 ready 不代表实际工件接续；部分迟到回调目标不存在时记为未覆盖。见 `evidence/cp4/figure-sources/historical/manifest.json:168–185`。当前计算摘要明确 `coverage_complete=false`、`target_met=false`，见 `figure-sources/calculations/policy-report-overview.json:5–8`。后来 16 个 HTTP 决策覆盖例补的是产品语义，不能倒过来补齐旧效果实验的每个场景覆盖。

当前控制面负载只能作失败诊断：059 的受限环境实际完成 256 条流程、1,280 次写请求和 32 次查询，256 条租约最终释放；虽登记 128 节点／1,024 卡，实际触达 4 节点／32 卡；耗时约 229.01 秒，普通请求 p95 约 9,207.64ms。来源 `evidence/cp4/partial_load_diagnostic_receipt.json:69,119–129,217,231–245`。提前中断后的原 run 缺完整结束字段，正式复核拒绝；不能把字段缺失当作唯一问题而忽略真实延迟失败，也不能从部分历史外推完整 50,000 命令的 p95。持久化全量状态的结构性增长诊断见 `evidence/cp4/storage-bottleneck-review.md`，不是“硬件不够”的证明。

## 3. 有条件发布需要什么，什么不能豁免

**可支持停止研究的证据**是问题分解、动作改变率、完整负结果、模型限制、有利／中性／反向实例，以及改动成本和收益空间的清楚比较。只有在明确受限的可行域和目标下，经过枚举、精确求解或可检查下界并与可行解吻合，才可称该实例或该域“不可改进”。目前局部 Owner 容量冲突证明只对那个小实例成立；没有覆盖完整工作负载、所有在线策略或全部存储架构的不可优化证明。

用户可以授权调整**团队自定**的发布范围，但不能把调整后的条件冒写成原 CP4 的成功，也不能改变官方契约。建议将两个记录并存：原 CP4 门禁保持真实状态；另建“受限演示／试点候选”的明确版本、用途、允许负载、已知限制和放行条件。这是可审查的范围决定，不是补一个 PASS 字段。本报告没有代用户作最终发布批准。

条件发布至少需同时满足：

1. 选定构建及核心契约／资源／权限／故障／恢复证据有效，没有已知核心缺陷。只读继承材料必须标原构建；最终合并候选如要称当前验收，按受影响范围产生当前材料。
2. 独立操作者从干净目录启动，B 的实际界面接通正确服务，三角色核心闭环、错误／部分成功／结果下载和刷新后身份行为确实完成。当前三项 NOT_RUN 不能以截图或自动换角色替代。
3. 若对外提供可持续服务，先实测并声明安全运行范围：包括累计工作／事件历史量、并发、运行时长、资源、响应与超时、恢复方式。全量状态成本随历史增长，仅限制同时在线人数不够。不能靠删历史、关持久化、隐藏慢样本证明服务可用。当前没有足够证据给出一个已认证的持续生产规模上限；本地受限演示与生产试点要分开。
4. 保留 R=1.00、规模／延迟失败、未验证 GPU 和算法假设；未验证的效率、收益或恢复时间承诺不进入界面或宣传。正式评测如另有已公布环境要求，必须满足或说明不满足。

不可用性能困境豁免的事项：冻结 HTTP 契约和鉴权；资源原子扣还、不超卖／重复分配／幽灵占用；租约到期／恢复预算／贡献者收回语义；真实执行与模拟边界；工件与工作身份归属；不得伪造事件、成绩、恢复事实或测试特判；来源与可复现交付。这些分别来自 `challenge.md:5,28–68,104–119,133,139–166,172–176`。第 133 行的官方门槛是特定问题触发最高 59 分，不能擅自扩写为所有自定目标失败都被官方淘汰；但“高质量放行”也不能容忍已知超卖或越权。

## 4. 值得路演的用户价值，和仍缺的对照

| 已有能力 | 超出最低状态接口的具体价值 | 可支持的表述与仍缺证据 |
|---|---|---|
| 稳定工作身份、分阶段提交、回执与失败后续动作 | 请求断线、租约成功但任务失败时，用户能找回同一工作并决定重试／归还，避免“点一次又开一份” | 基础幂等是必答题；把失败路径做成可执行闭环是产品价值。还需 B 换人实际完成部分成功和恢复，不能用 API 检查代替易用性。 |
| 主人合法收回、借用者可查中断、实际 CPU 工件接续 | 同时保留贡献者控制权和借用者已有工作；“收到了报告／验证了工件／新进程用了保存点”三种事实可分别追责 | 基本 reclaim 已是题目必需。固定 CPU 的实际进程停止、恢复结果等价是更强真实性证据。尚未有相同供给窗口下“安全冷重启 vs 保存接续”的完整成本收益对照，不能称减少训练损失 X%。 |
| Owner 隔离、授权贡献入口、管理员独立视图 | 不让贡献者管理权限越界到他人任务，借用者无法下载他人的结果，减少共享信任成本 | 多 Owner 隔离是基础项；可操作三角色闭环是增强体验。CPU 等价测试使用测试收回入口，不能单凭它证明普通贡献者 UI 收回；需结合授权 HTTP 历史与最终真人操作。 |
| 决策快照、候选受限说明、关联事件、完整持久状态重放 | 让管理者回答“为什么等待／是谁改变了占用／请求有没有真正提交”，对事故能查证而非猜测 | 16 个真实 HTTP 决策案例和私有 journal 证据成立；并不证明全球最优可行性、真实硬件能力或任意工作恢复。差异价值最好用一个陌生故障任务让另一操作者定位，记录实际操作成功与所需解释。 |
| 冻结报告、结果原始 JSON、图表逐项来源 | 评委能从结论追到原始输入与负结果，减少展示与实现脱节 | 588 个产物的来源审计是可追溯性，不是 588 个独立成功实验；应展示一个典型证据链和一个失败边界，避免拿文件数量充当价值。 |

若主张聚焦“连续性与可信操作”，最小新增机制对照可预先声明为一个固定 CPU 程序，在相同外部供给收回日程、预算、资源和结果目标下比较安全冷重启与已验证接续；记录总执行步数／重做量、保存与恢复开销、最终结果、贡献者等待及归还时间。至少保留有进度保存、零有效进度、恢复开销占优三种条件。测不到或控制不了开销时只报接续正确性，不写速度收益。不能故意破坏基线的资源／身份安全去获得“创新收益”。这是建议的少量新证据，不是已经完成的实验，也不要求重新启动 125 次策略搜索。

当前已有公平性保护诊断能制止平均值掩盖损害，但没有证明全局公平；贡献奖励／积分／成本回收只是可能产品方向，没有交易、结算、供给响应或真实成本对照，不能包装成现成经济系统。官方经济方向是可选项，见 `challenge.md:90–92`。

角色设计可改善，而不必增加后端权限：借用者默认“我的工作／下一步”；贡献者默认“我的供给／收回”；管理员默认“全局状态／事故／验收”。同一身份可以拥有多角色，角色切换是导航组织，权限仍由后端对象归属判定。首屏不应让所有人同时承担六种运维任务；六项能力可以作为工作入口、详情和管理员工具保留。新 UI 接入不能改动冻结 API，也不能以浏览器动画状态代替服务端事实。
