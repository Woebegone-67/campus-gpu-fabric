# 从题目重新判断织算的产品与路演主线

2026-11-15。独立审阅；不修改 Web，不替 B 定稿，不执行新性能实验。本轮依据为用户确认的仓库 `spec/official/challenge.md`，按基础可靠性55分、开放创新与工程证据45分判断。产品事实核对到候选 `059f477b9ea24578dda9426a3385e6ec97ba1cc1`；B 新设计只有两张截图，代码尚未上传。

## 结论

值得做角色首页，但它必须是能立即办事的首页。艺术表达可用于品牌入口和简短的页首；任务表单、状态、错误、资源数值应进入稳定、清楚的工作区域。若每次登录都要经过一张漂亮的角色介绍页，再进入原来难用的六区，问题没有解决。

本项目最值得讲的是一场具体冲突：**研究者还没算完，贡献者现在需要自己的卡；系统既要归还资源，也要让研究者知道保存了什么、还能否继续、下一步是什么。** 当前已有相当强的可核验接续证据，但普通抢占、保存、恢复本来就是题目必需能力，不能仅改名就算创新。继续争取创新分，须把“已经核验的进度”用于实际恢复顺序或时机，再用不利场景证明边界。现有 R=1.00 必须保留，角色首页的可用性改善不能替代策略收益。

当前不能宣传为已可供校园运行任意 AI 任务的平台：现有逻辑与 CPU 模式都不执行用户填写的镜像、命令和环境变量；CPU 是固定真实参考程序，GPU 库存仍为模拟。把这条边界放到提交前，优先级高于增加视觉效果。

## 2. 三个角色的真实需求应决定首页

“六区都有页面”是工程覆盖检查，不是用户为什么愿意使用的答案。首页应围绕角色当下最重要的决定组织，原六区可以保留为更深的工具与链接。

| 角色 | 他真正要解决什么 | 角色首页首先展示什么 | 主要动作与完成标志 | 不该放在首页的主角 |
|---|---|---|---|---|
| 研究者/借用者 | 找到能用的资源；工作停了不丢身份；知道结果和资源是否归还 | 我的进行中工作、需要处理的中断/租约、最近结果；当前执行能力明确可见 | 新建工作；继续上一项；查看阻塞原因；恢复/取消/归还。完成标志是结果或明确失败，加租约去向 | 全池管理员指标、内部epoch/revision大字、默认镜像JSON长表单、CP评分回执 |
| 贡献者/资源所有者 | 我现在能借出什么；需要时能按约拿回；自己的机器和数据边界可控 | 我的物理资源及真实占用状态、当前收回通知/截止、最近归还确认 | 开放或管理自己的资源；对选中资源收回；核对已释放/仍等待停止确认 | 借用者完整私有任务信息、管理员故障注入、未经实现的收益金额/贡献积分 |
| 管理员/运营者 | 有什么正在影响使用；谁需要帮助；事故能否解释、处理和复核 | 当前服务状态与数据更新时间、需要处理的异常、活动资源与近期事件入口 | 诊断一次等待/失败；查看当时决定；核对账本；查看实验与验收边界 | 每次进入先看巨大星空、静态“全球算力”数字、将未验项统一涂绿的系统健康分 |

这里的异常汇总、到期提示或影响范围若还没有相应投影，就列为待实现，不能由前端猜测。贡献者只能看到完成其职责所必需的影响摘要，不因“让他知道谁在用”扩大 Owner 数据可见性。角色主页是同一权威状态的不同视图，不是三套业务状态或三套身份系统。一个人拥有多个角色时，入口偏好不能代替后端授权。

推荐流程：

1. **研究者**：选择当前支持的运行方式 → 填资源与中断/结算偏好 → 确认提交 → 自动进入同一工作详情 → 等待/运行/停止/恢复都在该详情继续 → 领取结果并核对租约。高级配额、MIG、重试与超时展开查看；深链接直接打开工作，不强迫先过首页。
2. **贡献者**：我的资源 → 选择真实属于自己的卡 → 看通知期与截止/影响说明 → 确认收回 → 看到“已通知”“停止已确认”“资源已归还”的实际状态。不能用按钮 HTTP200 等同于资源已经物理腾空。
3. **管理员**：异常或用户问题 → 对应工作与当时事件 → 当时决定和实际提交结果 → 按权限处置 → 必要时在隔离实验复现。实验、验收与运行操作明显分开，避免误改主实例。

首页价值应通过小规模真人对照检验，而不是凭审美投票：同一任务、同一数据、两版顺序交叉；观察首次找到正确入口、完成操作所需时间、错误/退回次数，以及能否准确回答“现在是谁持有资源、是否真的保存、下一步是什么”。这些是拟做的产品测试，尚未获得任何效率提升数字，也不能用于替代策略R。

## 3. 对黑底点阵和“艺术主页+清爽工作台”的批判判断

本节只依据两张实际截图。未看到代码，不能断言帧率、CPU开销、键盘行为、动态对比度或缩小窗口后的表现已经不合格。

截图中能直接确认：星点从页首延伸到表单，灰色半透明输入框里仍可见高频图形；导航、标题、字段和较多说明同时争夺注意力；页面显示“服务未连接”和“非JSON响应”，同时仍摆出镜像/启动命令/资源配置。另一张只是完整背景图，不能证明这是实际数据可视化。

据此应分开处理四件事：

- **先恢复连接并确认执行能力。** 非JSON响应可能是代理/服务地址问题，截图不能定位根因。连接失败时应保留用户输入、禁用不能执行的提交、给出重试入口；不能用“空数据”代替不可用，也不能把后端延迟归咎于点阵。
- **把装饰留在不会影响读写的位置。** 黑色可以保留；正文与表单应有不透背景的稳定表面、清晰边界和文字层级。暂停背景是可取的补充，但默认贯穿工作区仍让用户先承担干扰。艺术页首是否动、是否跟随鼠标，是B取得真实代码后可测的设计选择。
- **解决能力错觉。** 当前 `Run.tsx` 可编辑 `image`/JSON `command`，下方才说明两模式都不执行它们。普通用户容易把填写 `train.py` 理解成会执行训练。应在首个操作区明确“逻辑任务”或“固定CPU参考程序”；不支持的镜像/命令不要当作普通有效输入。若需保留接口兼容元数据，应收进高级信息并标记实际用途。
- **避免主页变成额外路障。** 主页只有在它汇总待处理任务、常用入口、最近工作时值得做。品牌介绍可以单独直达；回访用户应能直接回到工作台。共享一套布局和状态组件即可，不需要先开发三套庞大首页、再重复一遍六区。

建议B保留点阵作为“织算”的识别资产，在品牌入口或较短页首试用；工作区保持平静。不要为追求“创新感”添加未经实现的全校算力地图、收益曲线或自动AI建议。若没有证据表明艺术首页提高理解或辨识度，其持续维护价值低于把工作详情做成能处理真实异常的页面。

## 4. 哪些算差异化，哪些只是已有常规能力

成熟系统已覆盖不少相似机制。HTCondor 的执行节点策略允许资源所有者控制何时运行、停止，并基于机器使用状态配置抢占；因此“利用闲置机器、主人需要时收回”不是全球首创。[HTCondor 官方文档](https://htcondor.readthedocs.io/en/25.x/admin-manual/ep-policy-configuration.html)

Kueue 已有配额借用/收回和公平抢占，能在团队之间重新分配被借出的份额；“多租户公平+抢占”也不能单独当作独创。这不是我们和这些产品的性能对照，文档研究更不能证明我们比它们更快、更便宜或更易用。[Kueue 官方文档](https://kueue.sigs.k8s.io/docs/concepts/preemption/)

当前可以形成竞赛特色的组合，是把校园临时供给中的双方承诺落到可操作对象：同一工作横跨停止与恢复；保存报告不自动升级为可信保存；实际接续必须绑定新执行代次；结果与归还分账；计划与实际提交分开。这些事实已有机制和测试支持。**组合清楚、边界诚实是优势候选，尚不是独创性或市场优势的证明。**

最弱的讲法是“我们有六个模块、很多测试、一个智能调度器”。更有价值的讲法是“主人取回卡时，借用者不用重新猜一遍发生了什么；每个继续/等待/失败都有可核对的依据”。它需要现场操作证明，还需要真人能正确理解的证据。

## 5. 只保留一个值得做深的创新主线

建议主线：**基于可核验剩余工作的连续性服务**。产品负责让借用双方看清一次中断的后果；新的决策机制负责在有限可用资源重新出现时，决定哪些已中断工作先接续、何时值得等待。这样把已有执行证据转化为会改变结果的动作，不再给同一项已选工作微调放置分数。

要研究的具体问题是：两个工作都能恢复时，一个已完成大半且保存点可信，另一个保存点无效或恢复成本更高；在不突破贡献者收回截止、不让其他Owner无限等待的前提下，使用这些已知信息能否降低全队列损失？“保护截止”是硬约束，“减少损失”是待证效果，“不让其他Owner受不可接受损害”必须保留反例测试。不能承诺没有资源时仍按时完成所有工作。

### 已有基础与待实现机制必须分开

| 已有、可核验 | 下一步才需要做 | 不应偷换成的结论 |
|---|---|---|
| 固定CPU程序有真实保存工件，验证后可用于新代次；与不中断结果比较的三类运行已保留 | 从核验工件提取当前进度，声明剩余工作的含义；测实际保存/恢复开销与有效期 | 已能预测任意训练任务剩余时长 |
| 回收、预算、等待、同工作ID、动作/实际事件链 | 策略能选择恢复顺序/时机；原P只选同一工作的放置，不具备此动作空间 | 新策略已比B2更好 |
| 当前Owner隔离及行为预算 | 新准入/恢复顺序的等待保护、回退规则；宽工作/小任务持续到达的伤害验证 | 加一个公平分数就有公平保证 |
| 完整队列与负结果的封存口径 | 用新输入验证有利、中性、逆向条件，再决定是否值得正式配对实验 | 复用旧125种子挑赢家或只报一例20% |

最小鉴别不应从再跑125次开始。先冻结一个小型、能推翻假设的集合：可信高进度/零进度对照；恢复开销低/高对照；兼容资源不足；另一Owner宽工作已久候；连续小恢复任务涌入；突然收回且本来就不可能同时满足双方目标。基线保留当前B2，并加入合理的先到先恢复/等待保护规则；不能用一个故意丢保存点或无效频繁重试的错误实现充当基线。

比较全体工作的F、完成数、最差Owner与个体损害、恢复预算、从保存点实际复用的工作和额外开销。所有失败/未完成留在原分母。若有进度也不能改变动作，或收益一旦加上开销/等待保护就消失，应停止该方向并封存负结果。只有行为变化、效果和伤害边界同时站得住，才值得冻结新正式输入。**本报告没有实施或验证这个新策略，不解除上一轮性能冻结。**

这个方向的创新价值比“再做一个首页”更接近题目20分创新和15分效果要求；首页与中断详情使它能被用户理解。若时间不足，展示已实现的可信接续原型和明确研究边界，比用概念动效掩盖算法零收益更有说服力，但仍须承认创新实证不足。

## 6. 用户价值和落地短板：不编市场数字

按当前55/45评分，以下不是单独70分，也不是要求现在去做收费市场。它们影响创新的实际价值、操作体验与现实迁移可信度。

最合理的首批对象是假设中的**同一学院、已有互信的少数实验室**：资源贡献者和任务使用者都能找到负责人，有现成局域网与管理员。跨校陌生人自由上传镜像、自动计费的开放市场，会额外引入执行隔离、数据与密钥、网络/驱动兼容、成本归属和责任处理；当前没有证据支持它已经可行。

| 尚缺的事实 | 下一步可执行补强 | 输出应长什么样 |
|---|---|---|
| 用户是否真因“找不到/不敢借/怕收不回”而放弃闲置资源 | 让借用者、贡献者、管理员分别复述最近一次真实借用/收回经历；询问替代方式、失败成本与不愿共享的原因 | 去标识的原问题记录和反例；不能把题目背景当访谈结果 |
| 新工作流是否比群消息/现有控制台更容易理解 | 用同一真实场景做当前六区与新角色入口的交叉操作观察，记录任务时间、错认状态与人工协助次数 | 原操作记录、成功/失败、参与者范围；不用小样本声称全校效率提升 |
| 贡献者为什么愿意持续加入 | 先验证可收回权、真实归还通知、低维护成本是否足够；积分/优先额度仅作为待测试方案 | 哪些激励被接受、哪些被拒绝；不要展示虚构积分或货币收入 |
| 真实AI工作能否在这里运行 | 明确单一执行适配目标、受控任务类型、保存协议、数据/环境要求，先做一个可重现小型真实任务 | 部署步骤、实际结果、限制与成本；当前固定CPU验证不能替代 |
| 可持续性是否成立 | 记录部署/运维人时、保存存储量与传输量、重算耗时；比较原有做法，不先填云价和收益 | 测量项和假设表；“可借GPU小时”不等于“有效完成工作”，账面释放不等于省电 |

成本讨论应保持可检查的结构：一次有效完成工作的实际运行、被丢弃的重算、保存/恢复、存储/传输及人工处置分别记录。还没有真实GPU、真实使用者与价格基础时，不给出省钱百分比、市场规模、盈利预测或推广承诺。借用者与贡献者是两个需要验证的群体，只有借用需求、没有可靠供给并不构成可持续服务。
