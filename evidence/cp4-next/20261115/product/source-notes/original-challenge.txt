Campus GPU Fabric
赛题定位：规范驱动 · ⾃主系统实现 · 动态场景验证 · 开放创新
接⼝约束：api/openapi.yaml 是本届⽐赛不变的公共 API 与测试控制接⼝规范。本赛题不新增、
删除或修改其路径、字段、枚举、鉴权头或响应语义；选⼿的创新通过内部架构和向后兼容的扩展能
⼒体现。
1. 背景与挑战
校园、实验室和科研团队拥有型号、显存、拓扑、可⽤时段各异的 GPU。部分 GPU 来⾃个⼈或课题组⾃
愿贡献：空闲时加⼊资源池，需要时贡献者有权收回。使⽤者希望像使⽤统⼀计算平台⼀样申请 GPU、运
⾏训练或推理任务，却不能假设资源永远在线。
静态分配容易；真正困难的是在资源不断变化、任务竞争、租约到期、贡献者回收、Checkpoint 失败和
节点故障时，仍然保证资源账本正确、任务状态可解释、恢复⾏为可信。进⼀步的问题是：如何在可靠性
的基础上，设计公平、⾼效、低成本、⾯向真实 AI 负载的系统？
本届⽐赛要求参赛队伍从零或基于开源组件构建⼀套可运⾏的 GPU 算⼒池 Server。公共 API 是互操作底
线，⽽⾮作品的全部价值。选⼿可以选择内存/事件驱动模拟、容器化实现、Kubernetes/KWOK 控制
⾯、混合架构，或其他合理⽅案；不要求购买真实 GPU。
2. ⽐赛模式与边界
主办⽅不提供可直接连接的完整算⼒池 API Server、现成 Dashboard 或参赛者可直接复⽤的完整参考答
案。参赛者提交的是⾃⼰可启动、可评测的系统，⽽⾮已有平台的客户端。
主办⽅提供：
1. 本赛题描述与冻结的 api/openapi.yaml；
2. 公布的基础测试⽤例、代表性资源/负载场景描述及评测⼝径（以赛前发布的评测资料为准）；
3. 评测环境约束、验收步骤和必要的测试账户/密钥使⽤说明；
4. 使⽤现有 /_test/* 接⼝进⾏⿊盒测试的说明。隐藏场景、不同种⼦与组合事件可⽤于最终评测。
边界说明：openapi.yaml 未规定独⽴的“导⼊任意节点拓扑”HTTP 接⼝。各队可以通过启动配置、数据
⽂件、内部管理界⾯或⾃身扩展接⼝准备模拟资源池；评委不会假定存在⼀个新的公共 API。主办⽅在正
式评测前应公布场景初始化、重置后的初始资源、环境变量/⽂件挂载约定及对应核验⽅法；不得要求选⼿
猜测未公开的初始化⽅式。/_test/reset 和 /_test/clock 的⾏为以冻结规范为准。

3.2 异构资源与⼀致性
⾄少管理 CPU、内存、GPU 数量、GPU 型号、显存和 MIG-like proﬁle；⽀持多 Owner 隔离、租约/过
期/续租、并发申请、Idempotency-Key 幂等，维护可审计的资源账本。
allocation 状态使⽤规范中的 Pending、Allocated、Running、PreemptRequested、Preempted、
Released、Expired、Evicted、Rejected。需要说明状态转移条件、资源占⽤与归还时机、⾮法转移⾏
为。核⼼资源不能超卖；释放、过期和故障后不应遗留幽灵占⽤；重复请求不应创建重复分配。
3.3 贡献者抢占与恢复
必须实现并可观察以下过程及其合理分⽀：
Running → PreemptRequested → Preempted → Pending/Allocated
⽀持抢占通知、截⽌时间、抢占事件记录、通知期内新 Job 的处理、Checkpoint ready/failed、到期资
源回收、通过 resume 或规范允许的等价机制恢复，以及⽆兼容资源时的等待。必须考虑失败后不虚报成
功、不⽆限密集重试、不突破重启预算。

景 ID、请求序列或种⼦来返回预写答案；评测将包含未公开的合法输⼊组合。

5. 模拟实践与真实性要求
⽐赛不要求真实 GPU，也不强制指定仿真框架。核⼼是可核验的状态与资源⼀致性；进阶性能⽐较需要清
楚声明的模型、输⼊与证据。
建议采⽤分层思路：
控制⾯：Kubernetes/KWOK 或⾃研状态机，维护节点、Pod/Job、租约、调度和资源状态。KWOK
可模拟 Kubernetes 资源⽣命周期，但不⾃动提供真实 GPU 运算性能。
⼯作负载层：合成任务、基于 Trace 的任务到达与时⻓、可选真实⼩规模运⾏及其性能 Proﬁle；为推
理和训练声明不同的需求或优先级。
环境事件层：逻辑时间、贡献者回收、节点状态变化、429/5xx/延迟等故障；通过已有测试接⼝驱动
可观察状态。
可选⽹络层：根据合理假设模拟拓扑、带宽争⽤、Checkpoint 传输与迁移，或⽤ SimGrid 等⼯具做
独⽴分析；不把未经校准的模拟结果冒充真实硬件测量。

9. 设计⾃由与验收底线
本赛题不是规定⼀种标准架构，更不是让选⼿照抄指定模拟器。可以只做⼀个严谨的事件驱动内存系统，
也可以把 Kubernetes/KWOK、真实容器、复杂⽹络模拟或现有调度框架集成进来。两者均有机会取得⾼
分。
但必须守住三条底线：
1. 规范⼀致：冻结 API 可被统⼀测试，⽆论内部架构如何，资源账本和状态都应正确。
2. 结果真实可证：模拟结果注明假设，实验可重放，性能收益有基线和不利场景作证。
3. 创新可解释：能够说明⾃⼰的选择、适⽤边界与失败模式，⾯对新的合法场景能运⾏，⽽⾮只演示预
先准备好的流程。
最终⽬标：让不同队伍围绕同⼀公共契约，探索不同的弹性异构算⼒池⽅案，⽐较的不只是“代码是否跑
通”，更是复杂动态环境中的系统设计、⼯程可靠性和研究判断能⼒。
