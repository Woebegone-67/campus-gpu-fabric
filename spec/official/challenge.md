# Campus GPU Fabric

> **赛题定位**：规范驱动 · 自主系统实现 · 动态场景验证 · 开放创新
>
> **接口约束**：`api/openapi.yaml` 是本届比赛不变的公共 API 与测试控制接口规范。本赛题不新增、删除或修改其路径、字段、枚举、鉴权头或响应语义；选手的创新通过内部架构和向后兼容的扩展能力体现。

## 1. 背景与挑战

校园、实验室和科研团队拥有型号、显存、拓扑、可用时段各异的 GPU。部分 GPU 来自个人或课题组自愿贡献：空闲时加入资源池，需要时贡献者有权收回。使用者希望像使用统一计算平台一样申请 GPU、运行训练或推理任务，却不能假设资源永远在线。

静态分配容易；真正困难的是在资源不断变化、任务竞争、租约到期、贡献者回收、Checkpoint 失败和节点故障时，仍然保证**资源账本正确、任务状态可解释、恢复行为可信**。进一步的问题是：如何在可靠性的基础上，设计公平、高效、低成本、面向真实 AI 负载的系统？

本届比赛要求参赛队伍从零或基于开源组件构建一套可运行的 GPU 算力池 Server。公共 API 是互操作底线，而非作品的全部价值。选手可以选择内存/事件驱动模拟、容器化实现、Kubernetes/KWOK 控制面、混合架构，或其他合理方案；不要求购买真实 GPU。

## 2. 比赛模式与边界

主办方**不提供可直接连接的完整算力池 API Server、现成 Dashboard 或参赛者可直接复用的完整参考答案**。参赛者提交的是自己可启动、可评测的系统，而非已有平台的客户端。

主办方提供：

1. 本赛题描述与冻结的 `api/openapi.yaml`；
2. 公布的基础测试用例、代表性资源/负载场景描述及评测口径（以赛前发布的评测资料为准）；
3. 评测环境约束、验收步骤和必要的测试账户/密钥使用说明；
4. 使用现有 `/_test/*` 接口进行黑盒测试的说明。隐藏场景、不同种子与组合事件可用于最终评测。

**边界说明**：`openapi.yaml` 未规定独立的“导入任意节点拓扑”HTTP 接口。各队可以通过启动配置、数据文件、内部管理界面或自身扩展接口准备模拟资源池；评委不会假定存在一个新的公共 API。主办方在正式评测前应公布**场景初始化、重置后的初始资源、环境变量/文件挂载约定及对应核验方法**；不得要求选手猜测未公开的初始化方式。`/_test/reset` 和 `/_test/clock` 的行为以冻结规范为准。

## 3. 必须完成的基础能力（统一验收）

### 3.1 公共 API Server

按冻结的 `api/openapi.yaml` 实现：

- `/healthz`、`/v1/version`；
- `/v1/capacity`；
- `/v1/allocations` 及查询、续租、释放、checkpoint、resume；
- `/v1/jobs` 及查询、取消；
- `/v1/events`、`/v1/metrics`。

可使用任意合理语言、数据库、消息队列、容器编排或部署方式。HTTP 可观察行为必须与公共规范一致。可扩展但不能破坏核心语义；不可要求评委访问私有数据库或安装特殊客户端才能完成基础验收。

### 3.2 异构资源与一致性

至少管理 CPU、内存、GPU 数量、GPU 型号、显存和 MIG-like profile；支持多 Owner 隔离、租约/过期/续租、并发申请、Idempotency-Key 幂等，维护可审计的资源账本。

allocation 状态使用规范中的 `Pending`、`Allocated`、`Running`、`PreemptRequested`、`Preempted`、`Released`、`Expired`、`Evicted`、`Rejected`。需要说明状态转移条件、资源占用与归还时机、非法转移行为。核心资源不能超卖；释放、过期和故障后不应遗留幽灵占用；重复请求不应创建重复分配。

### 3.3 贡献者抢占与恢复

必须实现并可观察以下过程及其合理分支：

```text
Running → PreemptRequested → Preempted → Pending/Allocated
```

支持抢占通知、截止时间、抢占事件记录、通知期内新 Job 的处理、Checkpoint `ready`/`failed`、到期资源回收、通过 `resume` 或规范允许的等价机制恢复，以及无兼容资源时的等待。必须考虑失败后不虚报成功、不无限密集重试、不突破重启预算。

### 3.4 黑盒测试控制接口

严格实现冻结规范中的：

- `POST /_test/reset`
- `POST /_test/clock`
- `POST /_test/contributor-demand`
- `POST /_test/node-state`
- `POST /_test/fault`

测试接口只在受控评测网络中通过 `X-Test-Key` 使用；不得作为普通用户功能暴露。不得通过识别固定场景 ID、请求序列或种子来返回预写答案；评测将包含未公开的合法输入组合。

## 4. 开放系统设计：选择自己的突破方向

完成基础规范之后，参赛者自主确定核心创新问题，并选择**至少一个方向作为重点成果**。下列方向是启发而非限定题目；也欢迎提出能够映射到公共资源、任务、事件语义的其他方案。无需全部实现；实现数量本身不构成高分理由。

### 方向 A：动态异构资源调度

面向 A100/H100/其他 GPU、不同显存、MIG-like profile、可用性变化和碎片化，设计 placement、排队、资源匹配或容量预测。可讨论同构优先、异构适配、碎片控制、抢占概率感知、显存利用与服务公平之间的取舍。

### 方向 B：贡献者友好型抢占与任务恢复

探索机会式 GPU 借用、提前预警、Checkpoint 时机选择、重启预算、恢复位置选择、连续抢占与防抖策略。重点展示“保护贡献者收回权”与“降低使用者中断成本”如何兼顾。

### 方向 C：面向 AI 训练/推理的负载感知管理

可以引入训练、推理、短任务、长任务、交互式任务的扩展工作负载描述；设计公平队列、优先级、SLO 感知、弹性放置、任务启动策略。公共 `/v1/jobs` 语义不变，高级元数据和调度控制通过内部机制或自定义扩展承载。不得声称虚拟节点真正执行了 CUDA 任务，除非提供可核验证据。

### 方向 D：分散资源池的网络感知与迁移

考虑节点间带宽、延迟、断连、Checkpoint 传输和存储路径。可选择解析模型、Trace 驱动、SimGrid 或自定义仿真；证明网络变化如何影响资源选择、恢复时间和任务完成率。此方向为选做，不要求所有队伍实现网络模拟。

### 方向 E：多租户、公平性与算力经济

设计配额、预算、优先级老化、公平共享、贡献回报、资源定价和用户解释能力。明确公平目标和系统资源约束，在不同 Owner 竞争下进行实验。

### 方向 F：可观测性、开发者体验与工程可信度

建设直观的任务/资源时间线、事件回放、告警、CLI/SDK/Web、审计与不变量监视；或实现真实 Kubernetes/KWOK、Kueue/Volcano/Lease/CRD 适配。界面需要有实际可操作的管理流程，不以静态页面截图替代功能。

### 方向 G：自定义研究型突破

允许提出上面未覆盖的方向，例如预测性资源供给、节能、博弈式贡献激励、在线优化、策略可解释性、形式化验证等；必须说明问题、度量、实验和相比基线的增益。

## 5. 模拟实践与真实性要求

比赛不要求真实 GPU，也不强制指定仿真框架。核心是**可核验的状态与资源一致性**；进阶性能比较需要**清楚声明的模型、输入与证据**。

建议采用分层思路：

- **控制面**：Kubernetes/KWOK 或自研状态机，维护节点、Pod/Job、租约、调度和资源状态。KWOK 可模拟 Kubernetes 资源生命周期，但不自动提供真实 GPU 运算性能。
- **工作负载层**：合成任务、基于 Trace 的任务到达与时长、可选真实小规模运行及其性能 Profile；为推理和训练声明不同的需求或优先级。
- **环境事件层**：逻辑时间、贡献者回收、节点状态变化、429/5xx/延迟等故障；通过已有测试接口驱动可观察状态。
- **可选网络层**：根据合理假设模拟拓扑、带宽争用、Checkpoint 传输与迁移，或用 SimGrid 等工具做独立分析；不把未经校准的模拟结果冒充真实硬件测量。

**不同实现可以使用不同模型，但比较时必须诚实区分**：

1. **规范合规成绩**：由统一 HTTP 黑盒测试决定，与仿真器品牌无关。
2. **策略相对成绩**：应在同一团队固定的输入和工作负载模型下，与至少一个简单基线进行配对比较；跨队绝对 JCT/吞吐量仅在主办方提供统一模型和输入时才可直接排名。
3. **真实性证据**：可用公开 Trace、Profile、真实小规模测试或有出处的模型参数说明假设；如没有真实 GPU，不扣基础合规分，但不能宣称已经验证真实 GPU 性能。

主办方可提供公开的示例 Trace/负载分布与隐藏同分布、分布外场景描述；在没有冻结统一性能计算器之前，不以不同队伍自报的“GPU 吞吐量”直接排名。

## 6. 评分标准（100 分）

| 维度 | 分值 | 判定重点 |
|---|---:|---|
| 公共 API 合规与资源账本正确性 | 20 | 必需接口、幂等、租户隔离、不超卖 |
| 生命周期、故障与租约可靠性 | 15 | 过期、并发竞争、注入故障、一致性 |
| 贡献者抢占、Checkpoint 与恢复 | 20 | 回收截止时间、失败处理、容量不足、连续抢占 |
| 核心系统创新及实际价值 | 20 | 问题价值、架构设计、机制原创性、真实可用性 |
| 策略效果与可复现实验 | 15 | 基线、对照、消融、负载变化与边界验证 |
| 可观测性、工程质量与迁移能力 | 10 | 可操作性、监控/事件解释、自动化、部署复现、迁移说明 |
| **总分** | **100** | **基础可靠性 55 分 + 开放创新与工程证据 45 分** |

**硬性门槛**：核心 API 未实现、基础资源账本存在可稳定复现的超卖/重复分配、无法完成基本的贡献者抢占回收流程，任一情形成立则总成绩最高 59 分。门槛样例和判定/复核步骤应赛前公开；未公布要求不作为追溯扣分依据。

**创新分不按模块数量累计**：一个方向研究得深入、证据完整，可以优于同时堆砌多个浅层功能的作品。纯静态页面、预置场景答案、未经验证的“AI 自动智能调度”描述，不构成充分的创新证据。技术栈选型本身不加分，关键是它解决了什么问题。

## 7. 测试与评测纪律

- 评委从干净环境启动作品，使用冻结公共 API 和既有测试控制接口观察行为，核心功能测试不读取数据库内部状态。
- 通过黑盒请求、事件、指标与状态变化核验，不依据源码语言、是否使用 Kubernetes 或是否购买真实 GPU 给予基础合规加分。
- 可使用独立 seed、重复运行、并发/故障交错与隐藏合法输入；公开输入范围与基本判定原则应赛前固定。
- 对性能实验，要求相同场景内的基线配对对照；如没有统一模拟性能模型，则不直接比较各队自报的绝对性能数值。
- 不允许特判测试种子、测试 Key、已知请求序列并硬编码成绩；不允许通过伪造事件、虚假资源状态或人为缩短逻辑运行时间取得成绩。
- 外部 AI 辅助、开源组件、代码生成均可合理使用，但必须申报关键来源、实际修改和验证方法。评委重视能否解释系统机制、调试陌生故障、复现实验，不将纯人工编码作为独立加分项。
- 正式评测的机器配置、网络权限、初始化方式、时间/内存上限及故障重测规则由主办方赛前统一公布。不得以未公布的依赖或设备要求淘汰作品。

## 9. 设计自由与验收底线

本赛题不是规定一种标准架构，更不是让选手照抄指定模拟器。可以只做一个严谨的事件驱动内存系统，也可以把 Kubernetes/KWOK、真实容器、复杂网络模拟或现有调度框架集成进来。两者均有机会取得高分。

但必须守住三条底线：

1. **规范一致**：冻结 API 可被统一测试，无论内部架构如何，资源账本和状态都应正确。
2. **结果真实可证**：模拟结果注明假设，实验可重放，性能收益有基线和不利场景作证。
3. **创新可解释**：能够说明自己的选择、适用边界与失败模式，面对新的合法场景能运行，而非只演示预先准备好的流程。

**最终目标**：让不同队伍围绕同一公共契约，探索不同的弹性异构算力池方案，比较的不只是“代码是否跑通”，更是复杂动态环境中的系统设计、工程可靠性和研究判断能力。
