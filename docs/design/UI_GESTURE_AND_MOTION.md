# 总览与工作台的滑动和转场规范

日期：2026-11-15。交付对象：B 的界面设计与前端实现。

本规范定义两个并列空间的切换：总览在左，工作台在右。用户希望在触控板上双指向左划进入工作台，反向返回总览；进入工作台时艺术背景逐渐退去，具体工作的身份和上下文继续保留。本次交付为设计与实现约束，尚未编写该交互、未测真实触控板，不构成手势兼容性或 UI 验收通过记录。

业务页面及数据来源见 [数据与组件映射](UI_DATA_AND_COMPONENT_MAP.md)。页面导航、权限、结果与原始业务状态仍由现有产品契约决定；滑动只改变所看的空间。

## 1. 可以承诺的体验和平台边界

### 1.1 产品约定

- 总览与工作台始终有可见、带文字的切换入口；当前空间有明确选中态。鼠标、键盘、辅助技术和触控板都能完成相同导航。
- 在实机验证通过的组合上，横向触控板滑动是自然的快捷入口。首次提示可写“在空白区域左右滑动，切换总览与工作台”，不必每次出现。
- 从总览点击某项工作，直接进入该工作详情；纯空间切换则恢复工作台上一次位置。两种进入方式采用相同视觉语言，但具有不同目标。
- 进入第二个空间不自动提交表单，不确认收回，不取消任务，不标记业务问题已解决。手势不能承担业务确认动作。
- 两个空间都能长期停留。工作台保留重要提醒，用户不需要反复返回总览检查异常。

### 1.2 原生手势不能被当成网页专属输入

Apple 将双指动作用于网页前后导航等系统交互；具体动作可在触控板设置中改变。界面不能要求使用者先关闭系统手势才可工作。[Apple 多点触控手势说明](https://support.apple.com/en-ie/102482)

网页通常接收到鼠标或触控板产生的 `wheel`，包括某些缩放动作；事件不等同于实际滚动，部分浏览器一串事件中只有第一项可取消。不能把“调用了 preventDefault”当成已经可靠取得整段系统手势。[MDN wheel 事件](https://developer.mozilla.org/en-US/docs/Web/API/Element/wheel_event)

标准 `WheelEvent` 提供横纵增量与单位，没有触控板手指数或稳定的“手指已抬起”字段。因此实现识别的是受限区域内的一段横向输入，而不是可靠检测“恰好两根手指”。不能用增量很小、设备名称、用户代理字符串推断出已认证的双指支持。[MDN WheelEvent](https://developer.mozilla.org/en-US/docs/Web/API/WheelEvent)；接口定义的来源可追至 [W3C UI Events 草案](https://w3c.github.io/uievents/#interface-wheelevent)。

设计可采用“两指左划”的使用语言；实现和验收材料必须同时保留上述边界。桌面触控板与手机触屏分开验收，不能把触控板的双指逻辑搬到触屏上而破坏缩放。

### 1.3 方向约定

以界面的空间关系和实际内容运动解释方向：总览向左退去，工作台从右边进入；返回时相反。自然滚动设置会影响用户手部动作与输入增量之间的对应，不能把 `deltaX > 0` 直接描述成“手指向左”。

实现统一一个内部方向 `toward-workspace`，在设备验证记录中列明：操作系统自然滚动设置、用户实际动作、收到的增量方向、内容运动方向。验收需包含自然滚动开与关，不要求产品修改该系统设置。如出现方向误解，优先跟随平台的内容滚动语义，并将提示改成“左右滑动切换”；不要以反转整个页面滚动换取字面上的左划。

## 2. 导航入口及范围

### 2.1 固定入口

桌面顶部保留“总览 / 工作台”两项切换，当前项有文字和位置反馈，不能只用两个圆点。点击也走同一套短转场，所以按钮交互不需要显得生硬。较窄窗口仍保留这两项，不能隐藏进只有手势才能找到的入口。

键盘按 Tab 可到达切换入口，Enter 或 Space 激活。若实现为标准 tabs，左右键只在该组件获得焦点时移动选择焦点；是否激活按既定 tabs 行为实现一致。不要全局占用左右键、Ctrl/Command 加左右键或浏览器前后退快捷键。可在“交互设置”关闭滑动切换；设置是表现偏好，不产生角色或数据访问权限。

### 2.2 允许起手的位置

第一版采用明确的区域白名单，先获得可靠性，再考虑扩大：

| 位置 | 是否可启动空间滑动 | 说明 |
|---|---|---|
| 总览的艺术背景空白、区域之间的空隙 | 可以 | 不包含任务标题、按钮、可选择文字或图形操作控件 |
| 总览页首名称与入口旁的非交互空白 | 可以 | 保留一个容易找到的起手区域 |
| 工作台页首的非交互空白区域 | 可以 | 工作表面内的常规滚动不承担切页职责 |
| 表格、代码/日志、文件内容、图表、时间线 | 不可以 | 即使当前正好没有溢出，也保留它们的独立交互语义 |
| 表单控件、可编辑内容及其内部标签/工具区 | 不可以 | 数字框滚动、选择、文本编辑不能引起离开 |
| 导航按钮、任务链接、菜单、拖拽把手、分隔条 | 不可以 | 由其自身的点击、拖拽或选择行为处理 |
| 弹窗、抽屉、打开的下拉菜单 | 不可以 | 整个空间切换暂停；不能从弹窗底下滑走 |
| 触屏内容区 | 本轮不承诺双指支持 | 保留原生缩放与纵向浏览；未来若加单指滑动须独立设计 |

B 应在原型评审时标出这两个起手区域，不将它们画成巨大空白以迁就技术。工作台内容密集时，顶部入口本身仍是可靠的主要定位点。若小窗口没有足够起手面积，滑动可以暂不可用，完整操作能力由可见入口提供。

### 2.3 必须拒绝的序列

以下任意一项成立时，该段输入交给原有控件/浏览器，不累积到空间切换：

- 起点或 `composedPath` 落在上述排除区域或嵌套滚动容器。横滚表格到边界后也不把剩余惯性交给整页。
- 页面已有非折叠文本选区；正在拖拽、调整列宽、刷选图表或使用输入法组合输入。
- 编辑控件保持焦点，或业务确认对话框、菜单、文件选择过程正在进行。点击切换入口依然遵循保留草稿规则。
- `ctrlKey`、`metaKey`、`altKey` 或 `shiftKey` 为真。尤其 Ctrl 组合可能是缩放，Shift 滚轮常用于横向浏览。
- 开始明显是纵向滚动，后来才出现少量横向分量；这一整段不得在中途升级为切页。
- 当前空间没有该方向的邻页。总览向更左、工作台向更右均不循环跳回。
- 当前页身份、授权上下文、epoch 或路由正在更换；目标空间已不存在；页面进入后台。
- 该段输入开始时无法获得可取消的事件，或浏览器已经开始原生滚动/历史导航。不得在原生导航过程中继续绘制一套独立转场。

## 3. 输入所有权与浏览器回退

不要在 `window` 或整个 `document` 上常驻一个拦截所有滚轮的非被动监听器。监听只作用于明确的起手区域；取消默认行为只用于已确认的横向切换。纵向输入和排除区域维持原来的浏览行为。

捕获存在取舍：等到横向累计很大才尝试取消，浏览器可能已经处理了起始事件；过早取消又会影响纵向浏览。第一版必须用真实设备验证这个窗口，不能把一套固定阈值包装成跨浏览器保证。未取得输入所有权前，不移动页面或先播放背景消失；避免产品和浏览器各动一半。

`overscroll-behavior` 可以控制滚动容器到边界后的行为，但它作用于滚动容器，不能被当成任意 DOM 元素上的系统手势屏蔽开关。只在需要隔离横向滚动链的容器评估使用，不以全局禁滚、全局 `touch-action: none` 或关闭浏览器默认设置解决问题。[MDN overscroll-behavior](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overscroll-behavior)

**退化规则：** 如果在某个目标浏览器、设备或嵌入容器中，一次动作仍可能同时触发应用切页和浏览器后退，该组合的滑动入口不得默认上线。保留可见切换入口与同样的转场，明确“此环境请使用上方切换”。不能通过识别某个浏览器名称就宣称已解决；也不能要求用户安装扩展或更改系统手势。

## 4. 状态机

状态机只管理表现，不写入工作/租约/设备业务状态。将输入识别与最终导航分离，方便用少量确定性事件序列检验。

| 状态 | 含义与输出 | 允许的下一状态 |
|---|---|---|
| `idle` | 没有待处理序列，显示稳定空间 | `candidate`、明确按钮导航 |
| `candidate` | 起点合法；观察主要轴和输入可取消性；页面尚不位移 | `tracking`、`native`、`idle` |
| `native` | 本段已判定为原生滚动/缩放/不受支持输入 | 输入安静后回 `idle`；不可中途转为 `tracking` |
| `tracking` | 横向方向锁定，获得输入所有权，显示有限跟随预览 | `settling`、`canceling` |
| `settling` | 本段已达到切换条件；导航只提交一次，视觉收束到目标 | `cooldown` |
| `canceling` | 未达到条件或发生可恢复中断；回到原空间 | `cooldown` |
| `cooldown` | 忽略同一手势的惯性尾巴，不反向再触发一次 | 达到冷却与安静条件后回 `idle` |

### 4.1 识别顺序

1. 在新序列起点确定源空间、输入区域、身份作用域和排除条件。后续即使指针经过另一块区域，也不能重新开始同一段手势。
2. 累计横纵分量。纵向先取得明显优势，则进入 `native`；方向不明确时不显示转场。
3. 横向达到启动阈值且仍可安全取得输入所有权，锁定轴与方向。此后不因轻微抖动切换轴；微小反向输入只减少预览距离。
4. 按有上限的累计距离更新局部跟随。不能用速度突峰作为唯一提交依据。
5. 达到提交阈值则发出一次 `navigate-space` 意图，进入 `settling`；未达阈值且序列结束则 `canceling`。预览期间不写 URL，不挂载第二份会发重复查询的业务实例。
6. 结算后进入 `cooldown`。固定冷却时长结束还不够，必须再等输入安静；持续惯性不能触发第二次切换。
7. 一次输入序列至多产生一次最终导航。两页不循环，所以强力一划也不会回到原页。

### 4.2 反向、取消与打断

- 达到提交阈值之前，明显反向并回到起点附近：取消，平稳归位。不会变成向另一方向提交。
- `Escape`：在尚未提交的预览期间取消；已有弹窗时 Escape 仍由弹窗处理，不由页面手势抢走。
- 提交阈值已达：不因惯性中的一个反向脉冲反悔。下一次独立手势才可返回。
- 窗口失焦、页面隐藏、尺寸/方向大幅变化：清除待识别输入；跟随预览立即或短时间归位，不恢复一个过时手势。
- 身份变化、登出、epoch 变化：取消转场，并先清除旧身份的敏感内容，再绘制新的状态；禁止将旧数据做淡出动画继续展示给新身份。
- 转场尚未提交时点击明确导航：取消预览并执行一次明确导航。已经提交后再次点同一目标无操作；点相反目标最多保留一个最新导航意图，在本次收束后执行，不堆积点击队列。

### 4.3 第一版调参起点

以下数字是**建议的原型初值，未实测、不是平台标准，也不是验收成绩**。B 应把它们集中配置，记录一次校准后的取值及设备，避免在组件各处出现不同魔法数字。

| 参数 | 初值建议 | 目的 |
|---|---:|---|
| 横向候选累计量 | 18 CSS px | 过滤很小的横向抖动；尚未取得所有权则不展示位移 |
| 横/纵优势比 | 1.8 | 与常规纵向浏览分开；用绝对累计量比较 |
| 提交累计量 | 96 CSS px | 需要有意的横向动作；不直接由单个高速度事件决定 |
| 跟随最大位移 | 可用宽度的 18%，最大 180 CSS px | 预览有限空间关系，不让小手势把整张工作表拖出屏幕 |
| 明显反向量 | 24 CSS px | 与微小抖动区别；仅在未提交时参与取消判断 |
| 事件间安静间隔 | 180 ms | 估计一个序列结束；不是可靠的“手指抬起”检测 |
| 提交后最短冷却 | 550 ms，且满足安静间隔 | 防惯性重复切换 |
| 归位动画 | 140 ms | 轻量取消反馈 |
| 明确按钮/任务入口转场 | 280 ms | 点击也保持空间连续性 |
| 提交后剩余收束 | 160–240 ms | 跟随已发生，不再完整播放一次长动画 |

只在第一版通过的 `DOM_DELTA_PIXEL` 输入路径使用上述像素阈值。`deltaMode` 为行或页时，不硬套像素数；第一版让其走原生行为/按钮入口。不能拿行高乘法当成真实触控板距离标定。也不能拿像素模式证明设备一定是触控板。若后续扩展其他模式，须追加真实设备记录。

## 5. 视觉转场分镜

### 5.1 固定层

品牌名、当前身份入口、总览/工作台切换器、服务连接状态保持位置稳定。转场中不旋转、不跟随鼠标、不退出视野。两页的文字、状态色与任务命名保持一致。

艺术层独立于业务表面。输入框、表格、错误反馈始终有稳定的不透明背景，不通过降低整个页面透明度制造“艺术感”。艺术层结束后停止绘制或卸载其动画循环，而不是只把看不见的高成本画布盖住。

### 5.2 总览进入工作台

| 转场进度 | 视觉变化 | 内容约束 |
|---|---|---|
| 0–20% | 总览轻微左移，工作台的空间位置可感知 | 名称、状态和操作标签仍清楚；业务内容不被点阵覆盖 |
| 20–65% | 艺术层逐渐淡出，稳定的工作表面接入 | 不新增大量粒子、景深、旋转或发光；不要让星点穿过文字 |
| 65–100% | 工作台布局稳定，标题和选中对象落位 | 任务详情可读，输入/滚动准备就绪；无需等背景表演完才可操作 |

采用单一的横向空间运动与透明度变化即可。不要同时加入镜头缩放、卡片翻转、文字逐字出现、弹性回弹与路径飞行。清爽的工作台可以使用暗色，转场不要求从黑变白。

### 5.3 点击任务与纯空间切换的差别

- **点击任务：** 将任务 ID 作为导航参数传入，保留名称与状态这个识别锚点。可用简短位置过渡帮助用户找到工作台中的同一任务，但不能复制出两个可操作对象。装饰克隆应从辅助技术和交互中移除。
- **纯空间切换：** 不根据鼠标最后经过哪项任务猜测目标。恢复上次工作区、筛选、排序、选中对象、滚动位置和草稿。
- **点击本人设备：** 采用相同规则进入设备详情，不把借用者私有任务内容顺带展示出来。
- **没有历史工作台状态：** 进入默认“我的工作”；存在合法深链接则优先遵循深链接，不先绕总览。
- **返回总览：** 回到原位置；已经解决的事项可以正常更新，但不在转场中突然重新排序所有行。

## 6. 草稿、请求、焦点与实时变化

### 6.1 状态分层

| 类型 | 切页行为 |
|---|---|
| 后端业务状态 | 共用同一权威查询与命令链；不因两页各自可见而产生两份真相 |
| 视图状态 | 保存当前空间、工作区、筛选、排序、选中项、各自滚动位置 |
| 未提交输入 | 同一身份会话中保留；切页不是提交、清空或取消 |
| 身份与凭据 | 遵守当前内存会话约束；不得为恢复页面将 token 写入持久浏览器存储 |
| 装饰状态 | 可以重新生成，不必持久化每个粒子的位置或动画进度 |

保持两页状态不意味着保持两套后台轮询。数据层去重同一对象查询；不可见的艺术动画暂停。表单可由共用草稿状态保留，也可保持必要组件挂载，但不能为动画加载第二个提交表单或重发登记请求。

已经发出的合法业务命令不因切页而被假装撤销。请求结果未知时，两页都应显示同一未确认状态并保留稳定工作身份。迟到响应必须经过现有身份/版本检查，不得覆盖新身份、新 epoch 或更新的查询结果。

### 6.2 URL 与浏览器历史

- 跟随预览不写历史；最终导航只写一次。沿用产品路由规则，不建立与 URL 脱节的第三套页面状态。
- 直接打开工作/设备深链接进入对应工作台；刷新后身份重新应用前不得把无权限结果解释为空任务。
- 浏览器后退/前进按真实历史导航，不拦截 `popstate` 强迫用户留在应用。应用内滑动不能同时产生一次应用导航和一次浏览器历史跳转。
- 已有工作详情、决策与事件链接保持兼容；新外壳不能使旧验收链接失效。

### 6.3 焦点和辅助技术

使用可见入口切页时，焦点可保持在当前选中的入口；通过任务链接进入详情时，将焦点移到详情标题或主要内容起点，避免键盘用户停留在已经不可见的任务链接上。返回时恢复仍然存在的原触发项；若对象已移除，回到该列表标题。

非当前页不能继续响应 Tab、点击或屏幕阅读器浏览。可采用正确的 `inert`/可见性组合；不要只用 `opacity: 0` 把仍可聚焦的表单藏在屏幕后。页面变化只进行一次简短的礼貌播报，艺术画布不进入阅读顺序。不能逐帧更新 `aria-live`。

### 6.4 转场时收到新消息

- 保存或任务状态变更先进入共用数据层；动效结束时使用最新合法快照。
- 一般进度更新不得自动切页、重排焦点或覆盖正在编辑的内容。
- 任务中断时在工作台保留简洁提醒；系统正在自动处理的等待，不升级为必须返回总览的警报。
- 当前对象被删除/失权：结束转场并显示明确的无权访问或不可用状态，不继续展示缓存为成功。
- 收到错误时，不为“保持动画顺滑”延迟必要的用户反馈。错误文案位于稳定表面，不在移走的背景里。

## 7. 减少动效与暂停

系统的 `prefers-reduced-motion` 表达减少非必要运动的偏好；本产品据此关闭大幅平移、视差和持续背景动画，保留立即切页或极短的透明度变化。导航能力和焦点结果相同。[MDN prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion)

用户选择暂停背景后，装饰静止，但业务进度照常更新。减少动效和暂停背景不是同一个开关：前者影响页面转场和动态表现，后者仅影响背景。产品不自行改变系统设置。两项偏好可以在不包含身份秘密的表现设置中保存，但保存范围应服从整个产品的隐私设计。

第一版不做自动循环的页面演示、不因闲置自动回总览、不以动画引导用户反复试滑。背景重启不触发任务查询风暴。切到后台、切到工作台或用户暂停时停止装饰绘制。

## 8. 实现拆分与可测试边界

建议 B 将能力分成四个可独立审查部分，而不是写在全局 `wheel` 处理器里：

1. **空间导航控制器：** 接收按钮、链接、已确认手势三类意图；负责一次路由提交、状态保存、重复意图合并。
2. **手势识别器：** 输入事件序列和允许区域，输出预览/取消/提交；不访问 API、身份凭据或业务写端点。
3. **转场表现层：** 接收源空间、目标空间、可选对象锚点、减少动效偏好和进度；不决定业务成功。
4. **共用数据与草稿层：** 沿用现有身份作用域和响应版本规则；负责两页一致性，避免为了动效复制业务逻辑。

首轮先用按钮完成同样转场，验证目标、草稿、焦点和业务状态，再接入受限手势识别。触控板功能通过实机矩阵后才默认启用。某组合未通过时单独退化，不阻塞其他输入方式，也不把未测试项标成兼容。

## 9. 必要测试与记录

本规范不要求重跑125次策略实验、性能完整负载或未受影响的后端路径。手势自动测试验证应用逻辑；真实触控板测试验证系统/浏览器交互，两者不能相互替代。

### 9.2 真实输入设备矩阵

| 组合 | 最少核验 | 当前状态 |
|---|---|---|
| macOS Safari + 内置或 Magic Trackpad | 左右切换、自然滚动开/关、浏览器前后历史存在时的冲突、惯性、缩放、表格横滚 | 未测 |
| macOS Chrome + 同一触控板 | 同上；不能继承Safari结果 | 未测 |
| Windows Edge或Chrome + 精密触控板 | 方向、横纵判别、浏览器后退、惯性；记录具体设备 | 未测 |
| 普通鼠标 + 键盘 | 完整导航、表单编辑、滚轮滚动；不需要模拟双指 | 未测 |
| 窄窗口/触屏设备 | 可见入口、原生纵向浏览/缩放、主要操作无裁切；不默认承诺双指切页 | 未测 |
| 嵌入式浏览器/评审容器 | 独立核对手势是否由宿主捕获；不自动继承桌面浏览器结论 | 未测 |

每个真实触控板组合至少手工往返五次，并执行一次纵向长内容浏览、一次横滚表格到边界、一次带未提交输入的往返、一次浏览器已有前后历史的操作。次数只用于发现常见误触，不构成统计可靠性结论。记录操作系统/浏览器完整版本、设备、自然滚动设置、入口区域、实际结果及误触；没有设备就保留未测或不支持，不填PASS。

录屏应同时能看见入口、页面运动和最终目标；必要时配合操作人的手势说明。合成 `WheelEvent` 成功只能证明识别器接线，不能证明真实双指或浏览器拦截行为。

### 9.3 放行条件

可见入口、深链接、草稿与身份隔离先通过。手势组合在规定起手区域不能出现双导航、无意提交、跳过确认、丢失输入或干扰内容滚动；仍有这些问题时关闭该组合的手势增强。动画掉帧先降级表现，不减少业务反馈或取消错误检查。

交付时由 B 列出“默认启用组合 / 可选试用组合 / 未支持组合”，附实际测试记录。旧 UI、结构草图或本规范均不替代该记录。此项完成也不能将 CP4 的其他未通过门禁改为通过。

## 10. 本规范中的事实与选择

平台事实来自上述 Apple、MDN 和 W3C 一手资料，检索日期为2026-11-15。双页空间关系、白名单区域、状态机、初始阈值、转场分镜和测试数量都是本产品的设计建议；需要在 B 的实际界面与目标设备上校准。本文不承诺网页能可靠识别手指数，也不承诺接管操作系统手势。
