# 同账户使用与贡献：后端第一批接入

日期：2026-11-15。分支：`work/account-capabilities`；基于已推送的 UI 交接提交 `42aea0010e528a99298be53b267e56d35777ebaa`。

这次落实普通账户同时使用算力和贡献设备，并提供可信账户能力查询。新双页界面、总览聚合、手势和 B 尚未上传的视觉不在本次实现中。它也不改变 CP4 尚未通过的结论。

## 产品含义

个人只有一个 owner 和一套凭据。使用与贡献是同一人的两类活动，不需要切换账户，不需要先成为管理员。Alice、Bob、Supplier 是示例名称，不再代表互斥职业；新的普通账户都可以提交工作、登记自己的设备、查询自己的贡献以及请求收回自己的设备。

管理员仍是独立授权。普通账户不能通过修改显示名称、页面模式、请求头或提交内容获得全局管理权限。拥有一台设备也不意味着可以读取使用该设备的其他人的任务、事件或工件；设备所有者可以收回自己的设备，运行方的中断与接续仍由原有内核负责。

## 兼容策略

内部凭据新增普通账户类型 `member`，要求非空 `owner_id`。业务模块统一检查能力，不各自维护“哪种用户允许哪个动作”的角色列表。

| 服务端配置 | `use_compute` | `contribute_resources` | 管理员权限 |
|---|---|---|---|
| 新普通账户 `member` | 是 | 是 | 否 |
| 旧 `researcher` | 是 | 否 | 否 |
| 旧 `contributor` | 否 | 是 | 否 |
| `administrator` | 是 | 是 | 是 |
| 内部 `system` / `test_driver` | 不授予普通业务能力 | 不授予普通业务能力 | 不等于管理员 |

保留旧两种类型是为了兼容已部署凭据，不是新产品的角色切换入口。当前没有任意能力编辑器，也没有组合角色不断扩张的机制。内部 Actor JSON 仍只有 `actor_id / role / owner_id`；能力由服务端计算，不接受客户端提交能力列表。

管理员的能力类别不等于每个动作都可执行。无 owner 的全局管理员不能冒用个人 owner 创建工作、登记个人设备或读取 CPU URI 工件。创建按钮至少还要检查 `owner_id !== null`，对象动作继续服从服务端状态与归属检查。

未配置 Bearer 的旧本地开发模式仍是受限 researcher，不能仅凭任意 `X-Owner` 获得贡献能力。B 的新页面应使用独立、已配置认证的开发实例。

## 新增接口

`GET /x/v1/session` 在核心 `campus_fabric.app` 和完整 `campus_fabric.workflows.devhost` 两种入口均可用。

请求沿用已有 Bearer 和 `X-Owner`。接口没有登录写入、角色切换、用户枚举或权限提升作用；直接读取认证结果，不读取或修改资源账本。

普通账户响应示例（无凭据）：

```json
{
  "actor_id": "alice",
  "owner_id": "alice",
  "capabilities": ["use_compute", "contribute_resources"],
  "is_administrator": false
}
```

- 200：已验证当前请求的账户。`actor_id` 和 `owner_id` 不一定相同，不互相替代。
- 401：缺少或无效凭据。不能沿用上一次账户的授权内容。
- 403：凭据和请求 owner 不匹配。
- 成功和错误响应均 `Cache-Control: no-store`，并带 `Vary: Authorization, X-Owner`。
- 请求追踪号在 `X-Request-Id` 响应头；成功正文严格只有上面四个字段。
- 不返回 token、测试密钥、所有账户列表或其他人的设备。

契约位于 [account-session.schema.json](../../contracts/generated/account-session.schema.json)，前端类型由它生成到 [account-session.ts](../../web/src/generated/account-session.ts)。不要手改生成物。`make contracts` 与 `make contracts-check` 同时覆盖原业务契约和此接口；冻结官方 OpenAPI 未变。

此处 `capabilities` 是**当前账户授权**。`GET /v1/version` 的 `capabilities` 是**服务实现能力**，例如真实 CPU 是否启用；两个对象不能混用。

## B 的接线次序

1. 保留自己的视觉提交，正常合入 `origin/work/account-capabilities`。这条分支包含完整 UI 交接版本，无需复制目录或覆盖另一方代码。
2. 启动自己的独立实例，导入该实例的身份文件。在真实业务请求前读取 `/x/v1/session`。
3. 同一导航下同时显示“我的工作”“我的设备”。这些是活动入口，不是切换凭据的按钮。
4. 使用能力控制功能入口、`is_administrator` 控制管理区。`profile === 'admin'` 或姓名 Alice/Supplier 只能作为显示信息，不再用于决定权限或发起管理区查询。
5. 对象操作仍读取 `legal_actions` 和对象状态；能力查询不能替代提交时的权限、版本、预算和停止确认检查。
6. 身份切换立即清理旧能力、旧数据和待显示提示；取消旧请求，并使用现有身份世代检查拒绝迟到响应。失败时不能假定“普通用户都能做所有操作”。
7. 未接入此接口的新旧服务组合应显示“账户能力尚未确认”，不能以 404 推断管理员或双能力；可保留已有兼容页面，但标明受当前服务支持的限制。

两页布局、注意事项排序和总览数据完整性仍按 [UI 设计说明](../design/UI_DESIGN_SPEC.md)。旧审计附录以 `059f477b` 为事实基线；本页覆盖其中“当前缺少双能力和 session”的历史描述，其他接口边界继续有效。

## 独立启动与既有实例

新实例沿用 [B 接管步骤](UI_B_HANDOFF.md) 的隔离目录和端口。`scripts/init_cp1_demo.py` 新生成的 Alice、Bob、Supplier 均为 member，Admin 仍为 administrator。生成文件仅保存在本机，权限为 0600；发现既有 auth 或 client-identities 文件就拒绝覆盖。

本次没有修改任何运行中实例的身份文件、数据库或凭据，也没有重启 A/B 的验收服务。仅拉取代码不会把旧 researcher/contributor 自动升级。

若确实要升级某个既有普通账户：实例负责人先在本机安全备份 auth 文件，仅将该账户对应记录的 `role` 改为 `member`，保留 token、actor_id、owner_id 不变；用新代码重启自己负责的服务，再通过 `/x/v1/session` 核对能力。不要改管理员和内部身份，不要把凭据、备份或 token 放入 Git/截图/报告。旧客户端文件无需重发。回退权限时恢复该记录原 role 并重启；回退代码前必须先恢复旧代码可识别的角色，旧代码不能解析 member。

建议 B 从全新的独立实例开始联调；既有 CP4 验收实例保持冻结，以免旧证据与新授权混淆。该手动升级流程是操作说明，本轮未对真实既有实例执行或代签。

## 本轮验证边界

结果与原始输出统一在 [本轮验证目录](../../evidence/account-capabilities/README.md)。定向验证包含：

- 旧凭据原权限、普通 member 的 owner 必填、内部身份不能走公开 Bearer。
- 新凭据生成与文件保留、权限模式、不泄露 token。
- 核心与完整 host 的账户接口、错误不缓存、伪造角色/能力无效、查询不改账本。
- 同一普通账户完成工作登记、资源分配、任务运行，同时查询和收回自己的贡献；两个人的工作与设备保持归属隔离。
- 混入他人设备的收回请求全部拒绝，不发生部分成功；跨 owner 工作读取/取消及伪管理员访问拒绝。
- 持久状态重启保留；查询提示与工作流采用相同能力判断。
- 相关既有权限、契约、HTTP、工作流回归及前端生成类型编译。

没有重跑125次策略比较，没有将本轮逻辑模拟写成真实 GPU 执行。新 UI 的接线、真实触控板手势和 A/B 真人完整验收仍待 B 合并后完成。性能阻塞和 CP4 放行条件没有降低。
