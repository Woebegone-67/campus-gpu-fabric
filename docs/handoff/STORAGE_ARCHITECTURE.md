## B 可以怎样继续

普通账户同时使用算力和贡献资源、`GET /x/v1/session`、总览/工作台设计与手势规范全部保留。先合入本分支，再基于 [账户能力说明](ACCOUNT_CAPABILITIES.md) 和 [UI 接管说明](UI_B_HANDOFF.md) 接线。正常合并自己的视觉提交，不覆盖整个 web 目录。

本次未改变冻结公共 API，也未要求前端理解数据库或增量树。单个租约/任务详情、公共容量使用专用读取路径；它们的权限、响应格式和可执行动作语义保持兼容。旧 ReadPort 仍有回退路径。工作详情仍返回完整关联历史；历史列表、管理员聚合和完整导出目前不保证常数成本，页面仍应使用已有分页、加载和失败状态。

不要把内部增量校验摘要作为用户的“任务进度”，不要把日志自洽叫作第三方公证。用户看到的仍是工作、资源、执行代次、结果以及真实归还状态。

## 解决的问题与取舍

原普通写入反复加载、复制、比较、序列化整份历史，还扫描终态任务寻找活动工作。历史增长会增加每一条新请求的成本，选择放置本身并非主要耗时。这与 CP3 放置策略 R=1.00 是两个不同问题，本次不改变该策略结论。

现在按实体延迟读取，只保存事务内发生变化的单元；活动租约、当前执行、待发送命令按索引选择。每条普通写入增量更新确定性的状态摘要，完整历史仍可独立重建。SQLite 继续使用 WAL、FULL 和跨进程单写事务，资源、事件、回执与待发命令一起提交。HTTP 读取请求体后的阻塞工作进入有限工作线程池，避免占住事件循环。

这不是消除所有成本：写事务仍串行；库存校验与放置仍依赖资源池规模；大量同时活动的任务仍需要处理；启动审计、迁移、完整重放和导出有意遍历全量历史。新增索引和树增加了磁盘空间、写放大与实现复杂度，必须由测量确认收益。

## 数据格式与旧实例

- SQLite schema 3：实体单元、查询索引、Merkle treap、提交日志和当前根同库同事务。
- schema 1/2 启动时迁移；旧日志原字节、顺序与原历史保留。只存在旧状态时记录明确的 migration-baseline，不补造更早历史。
- 原 schema 2 的 `fabric_state` 作为迁移原始副本保留，迁移后不再是当前状态。任何直接读取该表的旧运维脚本必须停止使用。
- 新日志为 `fabric-committed-state-v2`，独立重放支持 v1 前缀与 v2 尾部。完整 JSON 摘要在导出和独立 SQL 观测中计算，在线状态根由增量树生成。
- 不支持旧程序直接打开已迁移 schema 3 数据库，也不提供静默降级。拒绝识别不明结构或校验不一致的数据。

## 部署与回退顺序

1. B 首次开发使用新的 `runtime/b-ui-v2` 等独立目录。不要直接把新二进制指向 A/B 正在使用的旧实例。
2. 需要迁移已有数据时，先确认待迁移目录、停止该实例的服务与 CPU worker，确保没有活跃任务或未确认停止的执行。不要停止别人的实例。
3. 使用 SQLite 在线备份 API 或停机后完整备份数据库及相关工件、身份文件、配置；记录备份时间和原构建。不能只复制可能仍在 WAL 中写入的主数据库文件。备份及凭据留在本地，不入 Git。
4. 在独立目录的备份副本上用新构建启动，核对所有者、任务数量、结果工件、当前租约和独立日志重放，再进行 A/B 实操。迁移成功与产品功能验收分别记录。
5. 确认后才替换目标实例。新写入开始后，回退到旧备份意味着丢失这些新写入，必须显式确认处置方式；不能把旧 `fabric_state` 当作无损回滚数据。

本次开发没有修改现有验收实例的数据库、凭据、端口或运行状态。负载使用独立的 `cp4-load` 环境和新容器，禁止清理其他容器/镜像/卷。
