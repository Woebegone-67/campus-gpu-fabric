# 织算：交汇契约与验收规格

2026-11-14 · 待实施规格，不是运行验收记录

本文件让两个人可以连续开发、在固定节点真正接上。最终产品见[01](01_终态产品与独立复审.md)，责任边界和时序见[02](02_双人24小时正向开发作战书.md)。官方HTTP规范保持原样；以下对象是内部接口及独立扩展的设计，不给基础客户端增加必填字段。

## 1. 从输入到结算，身份和时间不丢失

| 对象 | 最小内容与语义 | 负责提供 |
|---|---|---|
| `CommandEnvelope` | actor/role、操作、参数、幂等键、请求ID；身份由服务端鉴权，不能信任body自报Owner | A |
| `CommitReceipt` | 结果/拒绝原因、对象ID、epoch/revision、逻辑时刻、关联事件ID、是否命中幂等；HTTP映射遵守冻结API | A |
| `WorkIntent` | 稳定工作ID、Owner、首次意图到达、allocation/job关联、执行模式、用户选择的结算动作、阶段结果 | B定义工作流，A持久写入 |
| `DecisionSnapshot` | epoch/revision、now、已出现的需求、当前库存/占用/租约/通知、允许使用的历史与元数据；不可变 | A |
| `DecisionPlan` | 快照版本、候选动作、前置条件、选中理由、同分规则、覆盖范围、策略/模型版本；无直接扣账权限 | B |
| `CommittedEvent` | 事件ID/顺序、逻辑时间、实体与attempt代次、实际触发请求/事件、状态和资源差量、decision引用 | A |
| `ReadSnapshot` | 已授权的同一revision视图；详情与列表注明版本；页面展示事实及合法动作，不能反向修改状态 | B消费A快照 |
| `EvidenceRun` | build、语义/模型/策略/场景版本、seed、输入、窗口、环境、输出、异常和计算脚本身份 | B；A提供执行核验 |

`WorkIntent`是完整产品与配对实验的对象，不是公开`JobRequest`新增必填字段。纯规范客户端依然只需按原API申请allocation、提交job。对这类客户端，没有共同意图时间就分别展示分配等待和job生命周期，不猜测用户何时开始想运行。

**跨层计时不能偷换。** 实验的任务到达由共同外部输入固定。等待allocation、job提交失败、恢复等待都属于同一工作。一个任务等100秒资源、再执行10秒，服务时长为110秒，不是10秒。失败或未完成不能通过更换ID、移出分母或提前结束记录消失。

同一逻辑工作可以关联多次合法attempt，但不等于允许任意多个job同时共享allocation。job与allocation的并用约束属于待明确语义，不能从UI方便性倒推。

## 2. 两个方向的交汇必须是单向、可核对的

### A向B：读事实，不能交出可变账本

- 快照和事件包含版本；B的查询、策略、实验分析不得持有可修改的领域对象引用。
- 普通Owner只能看到授权对象；管理员全局视图用独立受权扩展。事件和metrics也要检查泄露，而不只保护详情页。
- 状态提交和对应事件同事务落地。前端重连可按游标续读；收到旧epoch不能覆盖reset后的新状态。
- 事件的cause指实际触发关系，不等于证明一种策略造成了最终性能变化。性能归因仍要配对与消融。

### B向A：交计划，不能绕过合法性检查

- 策略只读当前快照，不读场景文件中的未来到达/回收/耗时，不访问评估器的隐藏完成时间。
- A提交前复查epoch/revision、权限、资源、租约、预算、执行代次与操作前提；失效计划返回可识别结果，重新计算或走已声明后备规则。
- 排序与候选生成可在锁外进行；检查和扣减不可拆开。一个decision的实际提交结果须回写记录，不能展示被拒的计划为已经发生的动作。
- 只有覆盖完整合法放置域或给出完备证据，才能写“当前全池不可行”。截断搜索必须标明范围；部分搜索失败不是全域证明。
- 候选数、解释成本、计划失效次数与后备策略触发次数进入统计，不能为漂亮解释无限阻塞调度。

### 产品动作的唯一写路径

普通用户和贡献者按钮走公共API或受权`/x/v1/*`扩展；测试密钥绝不进入浏览器。所有适配器调用同一命令内核。贡献者登记资源、收回自有设备及查询回执属于产品扩展，不能假装冻结API已提供这些操作。

allocation成功、job失败时保存部分成功回执，并提供对现有allocation提交job或释放的操作。自动结算是用户授权的持久工作流：完成后领取结果/失败原因，按选择处理租约；不能关闭浏览器就停止，也不能释放仍被其他合法工作使用的资源。

冻结POST /v1/jobs没有声明幂等键，不能假定重发安全。B的服务端编排器调用A的内部`create_job_and_bind(intent_id, stage_id, expected_revision)`，将创建、关联和阶段回执放进同一事务；相同阶段重试返回原结果，冲突参数拒绝。阶段回执先于任何成功响应持久化。纯规范调用的行为不因此新增强制请求头或意图字段，产品提供的工作流保证与基础API语义分别写清。

## 3. 三种“保存成功”分开，两个时间域分开

checkpoint的三层事实分别记录：

1. **收到报告**：规范接口收到`ready`或`failed`。没有artifact_uri仍按契约处理。
2. **工件已核验**：确实能读取、身份与完整性匹配，记录核验器和结果。
3. **执行已接续**：实际应用载入保存点，产生可核对的后续结果。

模拟执行只能报告模型中的状态和效果。真实CPU参考实验使用可保存的确定性任务、明确工件与重启过程，并与不中断参考结果比较。它证明该适配链，不能被称为任意CUDA程序自动checkpoint。

逻辑评测模式中，全部到期行为由逻辑时钟驱动。真实CPU模式中，实际计算/写盘/停进程有墙钟耗时；不能拨快clock就声称实际进程完成保存。模式、转换条件和测量单位写进运行记录。

**CP0固定两个独立实例模式。** 评测实例由测试方显式推进逻辑时间；CPU参考实例由一个驱动器按单调墙钟经过量，提交同一个逻辑推进命令。内核均只有一个逻辑时间和一个顺序处理器，不另外用真实sleep触发租约过期。人工clock推进仍进入同一队列，不能再被驱动器当作墙钟经过量重复计时。大步推进处理所有到期边界，但实际CPU停止/保存必须取得真实回执；未确认停止的资源先隔离，不重新分配。记录实际停止延迟，不能拿逻辑到期时刻冒充物理立即收回。两个模式的证据和吞吐结果分开报告。

控制面崩溃恢复须保留租约、工作绑定、幂等回执和事件。恢复后处理未决执行前先确认代次与存活情况；旧回调不能复活已回收资源。若无法确认旧执行已停止，保留隔离状态，不能同时把同一资源重新承诺给另一个真实执行。

单个CPU参考子进程的存活确认、旧代次隔离和安全接续属于正式目标；跨主机、多worker或实GPU执行的同类保证才是额外冲刺。不得把前者延后，再用“多进程属于冲刺”解释正式恢复缺口。

## 4. 同条件效果实验先固定口径

### 4.1 共同输入与五类检验

开发场景用于修改策略；最终验证场景的生成规则、参数范围和seed在验证前固定，验证集不再承担调参。至少五类场景、每类五个验证seed：

| 场景族 | 要区分的机制 | 必须保留的困难输入 |
|---|---|---|
| 兼容性与碎片 | placement是否真正保留其他需求机会 | 部分可行大任务；多个型号/profile；当前机会代理恒为0 |
| 波峰与多Owner | 准入/老化/份额如何影响有效服务 | 大小任务混合、同优先级、请求拆分、晚到Owner |
| 收回与保存 | 已知通知窗口和保存成本是否值得利用 | ready/failed/timeout、短窗口、连续收回、无替代资源 |
| 节点与交错故障 | 状态/重试/预算是否掩盖策略代价 | 掉线、超时后重试、迟到回调、同刻到期、恢复失败 |
| 中性与反向场景 | 复杂策略在何处没有价值或更差 | 稳定同质供给；无竞争；稀缺大任务与大量短任务冲突 |

上述五族全部进入主指标R，包括中性/反向族；不能只把有利的竞争/易失供给场景计入分母。每个效果run建议256—512项工作，以可读因果记录和完整配对为重点。10,000任务、50,000命令的规模压力另行测试，不把性能比较误变成几百万次HTTP请求才算完成。数量是自定覆盖目标，不能当作独立现实样本量或数学可靠性证明。

公开输入包括资源、需求到达、贡献者通知时刻和时长、外生故障。所有策略面对相同输入。内生故障不能按“该策略第17次调用”随意对齐：需按稳定的逻辑工作/attempt/操作身份绑定，或明确它本身就是独立压力实验。否则不同策略会遇到不同事件，结果不能简单归因。

### 4.2 基线和消融

统一合法性、工作量模型、checkpoint能力、失败处理和预算：

- **B0**：FIFO＋first-fit。
- **B1**：与候选相同的Owner公平准入＋best-fit。
- **B2**：B1加简单兼容稀缺性放置。其具体比较键、同分规则必须在验证前固定。
- **P**：待验证的机会/恢复策略。分别关闭机会组件与恢复成本组件；若组件未使用则不捏造消融。

B2应被当作真正竞争者实现，不故意选错误的装箱方向或关闭正常恢复。若最终成熟基线更好，它可以成为默认策略；产品的解释、恢复、实验能力依然成立，创新收益另据实判断。

### 4.3 主指标与损害

使用01定义的未兑现需求面积

\[
F^\pi(H)=\sum_{i:r_i\le H}[\min(C_i^\pi,H)-r_i],
\]

其中失败和未完成的\(C_i^\pi=\infty\)。这等于窗口内仍未完成工作数曲线的面积；不能叫纯排队等待。主动取消按共同输入和预先固定规则处理，不由策略选择性删任务。

每族先平均各seed的\(F_P/F_{B2}\)，再对族等权平均。目标\(R\le0.85\)；同时每个配对run完成数不下降。零分母单独报绝对差，不能悄悄丢掉候选退化。还需列每族最差结果，避免宏平均掩盖一整个场景失败。

个体比较\(\Delta T_i=\min(C_i^P,H)-\min(C_i^{B2},H)\)，严重损害暂定大于300逻辑秒。Owner有效服务低于自身正基线的80%也记严重损害；基线为0时只报绝对差。目标无新增这类损害。阈值验证前固定，全部差值/未完成身份保留。Owner服务单位来自同一声明模型，工作量不可直接跨类型相加时先按固定参考量归一化并公开权重。

配套展示：完成/失败/未完成数、allocation等待、job生命周期、尾部分布与删失数、重做损失、有效服务、资源占用、每次决策耗时。只对完成者计算的P99要明确样本范围，不能用它代替含未完成者的主指标。

### 4.4 因果与归因检查

修改或删除尚未到达的请求和通知，共同输入前缀内的决定、状态与事件应一致；固定内部随机种子和同分规则。改变模型隐藏的真实工期也不能被准入时提前感知。模型里可观察的进度及实际完成事件出现后，状态才允许分叉。

对机会代理记录非零覆盖率、实际改变动作数及计算成本；对恢复组件记录何时改变行为。总分变化、触发率与同状态替换各自回答不同问题，不把两条轨迹的差异直接称作原因。重要负结果连同完整输入留下。

## 5. 验收目标和证据格式

以下ID供所有checkpoint引用。`MET / NOT_MET / NOT_RUN`对应本团队目标；官方合同测试另列明确条款。通过有限测试不宣称证明所有并发历史。

| ID | 判据 | 需要的证据 |
|---|---|---|
| T-CONTRACT | 21操作均按冻结契约实现；基础不依赖私有数据库或特殊客户端；权限/错误/可选字段有覆盖 | 操作映射表、实际HTTP请求响应、未明确语义清单；schema解析不算运行通过 |
| T-STATE | 被检查历史中无超卖、越权、重复效果、幽灵占用、虚假恢复、预算越界 | 独立观察账本、并发历史、参考模型、失败序列与修复回归 |
| T-REPLAY | 事件重建与终态一致；在线行为对未出现输入保持前缀一致；reset隔离旧代次 | 回放差异、前缀对照、重复reset/迟到回调记录 |
| T-PRODUCT | 三角色六工作区真实闭环，完成提交、理解等待、续租/取消/恢复、收回及结果结算 | 换人操作记录；UI/HTTP关联；1440×900截图与空态/错误/部分成功检查 |
| T-POLICY | 五类×五seed匹配比较，B2与消融齐全；争取R≤0.85、完成数不降、无定义的新增严重损害 | manifest、完整输入/输出、逐族/逐Owner/逐工作差值、计算脚本、成本与负结果 |
| T-REAL | 持久控制面重启恢复；真实CPU保存—停止—恢复与不中断结果一致 | 独立进程退出/重启记录、文件工件、结果比较、旧代次清理；不拿模拟事件替代 |
| T-SCALE | 128节点/1,024物理GPU/64Owner/10,000任务/50,000混合命令/32并发下账本一致 | 声明拓扑、运行参数、并发历史、核验结果；MIG实例不重复当物理GPU计数 |
| T-LATENCY | 4vCPU/8GiB声明负载下普通查询/命令p95<200ms | 环境和命令、样本数、p50/p95/p99、吞吐、队列长度；注入延迟/clock批处理/实验分别报 |
| T-DELIVERY | 换人按README从干净目录启动、重现核心场景、视频与包同构建、实际上传有回执 | 启动记录、依赖锁、场景和原始结果、3—5分钟实际演示、AI/第三方来源 |

单条记录至少包含目标ID、状态、构建/输入版本、执行者、命令或操作、预期、实际、证据路径和未解决问题。没有执行的项目写`NOT_RUN`；界面不能从“测试脚本存在”推断`MET`。

## 6. 不容易被演示掩盖的攻击集合

1. **并发和幂等**：32请求争最后一份资源；同key并发/重发/断线后重发；同key不同payload；两个Owner使用相同key；提交成功但响应丢失。按正式契约及声明语义分别判定。
2. **资源与状态**：CPU/memory/GPU/VRAM/profile/标签不匹配；异构节点组合；MIG父子互斥与容量；多资源原子扣还；取消、释放、到期、驱逐路径都核对。
3. **收回与预算**：ready/failed/无报告；恰好deadline；通知期新job；重复收回；无替代；恢复失败；重试上限；HTTP重试不额外消耗业务预算。
4. **逻辑时间**：大步推进与按同一事件边界分步推进的结果一致；同刻顺序固定；中间外部输入相同才比较。真实CPU模式不套用瞬时计算完成假设。
5. **reset与迟到消息**：reset后旧attempt结果、超时回调和幂等记录不得污染新epoch；对重复ID与重启进行攻击。
6. **独立正确性**：小容量系统使用较慢、简单的参考模型核对状态与资源；并发记录检查是否存在满足真实先后关系的合法串行解释。不能用生产代码同一个计数器自证。
7. **崩溃窗口**：事务前、提交后响应前、保存中、回收与恢复交界杀控制面；重新启动后幂等和账本仍一致。核查实际CPU旧进程，而不只是数据库中把它标为停止。
8. **产品授权**：借用者尝试收回他人资源、读取他人事件/工件；贡献者不能借“管理自有资源”修改其他Owner任务；管理员与测试权限不同。
9. **工作闭环**：租约成功job失败、页面刷新/关闭后继续、结果下载失败、自动归还失败、取消与完成竞争。每个分支有真实可操作状态。
10. **策略反证**：当前机会分数全零、部分可行大任务、稀缺资源过度保护、连续被收回、稳定无竞争、高计算成本；同状态替换检验与全量得失都保留。

高难冲刺可把长失败历史自动缩减为更小反例；没有证明时不要称为全局最短反例。Kubernetes/KWOK或实GPU适配需实际运行证据，迁移设计文档另列。

## 7. 官方未细化语义：集中处理，不传播猜测

当前资料尚未完整给出初始化库存、reset后的场景、部分默认值和同刻事件细节。`SemanticsConfig`集中维护每项来源、暂定行为、影响接口、验证例和可替换点。官方说明到达后只修改对应适配及测试。

重点条目：TTL起算与renew省略body/default；一份allocation能同时承载几个job；checkpoint/resume对job的具体关联；重复贡献者通知；Draining/NotReady影响现有执行；non_preemptible与主人收回的优先关系；job重试和allocation重启的计数时机；fault匹配/默认参数；同刻到期、保存、回收顺序。

OpenAPI中fault mode的string类型与未加引号的数值enum、X-Owner的扩展说明与operation参数挂接不一致等，记录为原文件问题，不静默改写冻结文件。实现可做兼容适配并留下明确说明，但“我们这样决定”不能写成“官方已规定”。不阻塞所有已确定部分的正向开发。

## 8. 交付时最短阅读与运行链

最终实现应提供以下入口；它们是开发要求，**现在还不存在可声称运行通过的产品命令**：

- 一个README：安装/启动、测试密钥与普通账户、逻辑时间模式、UI地址、清理自己的实例。
- 一套配置：场景、语义、模型、策略、依赖版本；敏感密钥不入包。
- 一条核心演示运行链：提交→贡献者收回→保存/失败→等待/恢复→结算。
- 一条独立核验链：合同、账本、前缀、真实CPU结果与控制面重启。
- 一条效果复现链：manifest→配对原始run→指标→图表；每张图可定位输入和策略。
- 一份总验收：官方基础、产品正式目标、效果/规模争取目标、高难冲刺分层报告。未完成项写影响，不用空泛免责声明淹没已成立的成果。

这些入口实际完成后才填最终命令和通过状态。Checkpoint的作用是不断把同一个产品做完整，不是制造一串只能在各自机器上播放的演示。
