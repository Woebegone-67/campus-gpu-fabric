# 路演主张与评分策略

2026-11-15。依据：仓库 [challenge.md](../../spec/official/challenge.md) 的 **55 分基础可靠性 + 45 分创新与工程证据**。这是最终展示的设计与执行依据，不是验收通过书。后端候选与实测结果以本轮交付状态为准；新 UI 尚待 B 合入。最新实测状态见 [本轮交付状态](../handoff/FINAL_PREPARATION.md)。

## 1. 先回答最难的问题：我们现在值得被记住吗

我们已经有一个能够深入解释共享算力故障的系统原型，但还没有证据支持“新的调度方法显著提高了效率”。正式 P/B2 对照 R=1.00，是精确相等，不是四舍五入。新准入研究出现局部收益，也出现一个 Owner 从获得服务到完全失去服务的反例，所以没有上线。完整 CP4 仍未通过。

如果路演依然以“智能 GPU 调度平台”开场，再展示提交、列表、图表和几个绿色状态，评委看到的会是一套普通管理界面；一旦追问效率、真实执行和新颖性，叙事就会超过证据。换一套炫目的视觉、增加模块或堆叠测试数量，都不能修复这个问题。

**我们应该把主张收窄，同时把验证做深：共享成功的单位是一项真正接续并交付的工作，不是一条成功分配记录。** 让评委看到资源所有者和借用者的冲突，亲自改变一个合法条件，再用原始记录核对结果。真正留下印象的是一个能被追问、甚至可能失败的演示，而不是我们宣读“可靠”。

这是一条有辨识度的呈现方向，尚不是已证实的独创算法。要获得较强的创新与效果评价，还需要补机制的因果价值、代价和边界。演讲不能代替这些缺口。

## 2. 一句话、一个冲突、一件评委带走的东西

**封面：可收回的算力，可核验的接续。**

**开场冲突：你现在需要自己的设备，但另一人的工作还没结束。谁应该让步？**

我们不承诺把冲突消灭。设备所有者应能提出收回；借用者应知道工作保住了什么、失去了什么、下一步能做什么；管理者应能核对停止、占用和归还，而不是靠双方猜测。

整场只追踪同一工作。评委最后得到一份不含凭据的证据包：输入与构建、收回请求、保存点、停止确认、新执行起点、最终输出和核对方法。包里的数据能够推翻台上的话，才值得把它称为证据。

中心问题不是“你相信我们的系统吗”，而是：“哪一条记录，足以让你判定这次接续没有成立？”

## 3. 谁使用同一个平台

不是三套互斥账户，而是一个个人空间，加上明确授权的管理空间。

| 活动中的人 | 此刻的真实问题 | 总览先显示什么 | 工作台提供什么 | 不该强迫他理解什么 |
|---|---|---|---|---|
| 使用算力的人 | 我的工作是否在推进？要不要我处理？已有结果在哪？ | 需处理的中断/失败，其次正在运行和刚完成的工作 | 工作详情、合法恢复/取消、结果下载、原因与过程 | 数据库版本、执行协议、实验编号 |
| 贡献设备的人 | 我现在能收回自己的设备吗？多久、到哪一步？ | 我的收回请求、尚未确认停止的占用、可贡献设备 | 登记、可用窗口、收回及实际归还状态 | 借用者私有输出、管理员全局信息 |
| 管理者 | 哪些资源不能安全复用？谁受影响？系统有什么异常？ | 未确认停止、长期等待、服务异常等授权范围内问题 | 资源/租约/事件定位、隔离与审计入口 | 每个用户的全部私有内容；管理权限不等于任意读取工件 |

同一个人可以上午贡献设备，下午使用别人的设备；不需要退出再登录。能力由服务端认证返回，对象仍检查归属和状态。主线中的 Alice、Supplier 是两个普通 member，名称不代表职业；示例 A10 设备属于 Supplier，所以不能临时换 Bob 发起同一收回。A/B 指两位真实操作者。Bob 用于独立越权检查。管理员不参与完成普通用户本应自行完成的流程。

当前这是基于题目和流程的产品判断，尚无访谈数据证明各类校园用户的需求频率。不要把它包装成“已验证的全校刚需”。

## 4. 为什么原界面有强烈的 AI 模板感

问题不只是颜色和圆角，而是界面没有替用户做判断。

1. **开发结构变成产品导航。** 六个同等分量的工作区与 CP 编号暴露了实现过程，用户却只想找到自己的工作、设备和待处理事项。
2. **所有信息一样响。** 巨型标题、长解释、状态标签、空白卡片和按钮都有很高视觉权重，没有指出“现在最要紧的是哪一件”。
3. **实现字段代替任务语言。** 用户一进来就面对 image、JSON command、TTL、预算与 MIG-like；当前 CPU 参考模式甚至不会执行其中部分输入，造成错误预期。
4. **装饰没有业务含义。** 全屏动态点网、透明表单和发光文字持续争夺注意力；即使停掉动画，底图仍可能降低阅读清晰度。
5. **用说明文字补交互缺口。** “请核对”“以服务端为准”反复出现，却没有把状态、时间、原因和下一步放在一起。
6. **布局不随情境变化。** 等待、需人工处理、已完成都用相同长卡片，视觉上看不出用户此刻该不该行动。

双空间设计的价值是改变信息优先级。总览回答“现在需要我关注什么”，工作台回答“我要如何完成这件事”。艺术层只在总览的非文字区域帮助理解真实活动，不能随机制造繁忙感，也不能用空资源的动效暗示系统正在工作。工作台使用实底、清晰表格和局部强调。

横向切换提供连续的空间关系，但不是整个产品的卖点。双指左划只能作为增强输入；可见入口、键盘、减少动效和深链接必须同样完成任务。动效的淡出对应工作台获得注意力，而不是每次翻页播放一次广告片。详细行为沿用 [UI 主说明](../design/UI_DESIGN_SPEC.md) 和 [手势规范](../design/UI_GESTURE_AND_MOTION.md)。

## 5. 对照评分：每一段演示解决一个评审疑问

| 评分项 | 分值 | 评委最可能追问 | 主讲中给的回答 | 留在证据与问答的内容 | 不能这样冒领 |
|---|---:|---|---|---|---|
| 公共 API 与账本 | 20 | 有界面，但资源真的不重复分配吗？ | 同一设备占用、停止确认、归还三个时刻可核对 | 冻结 API、幂等/最后资源竞争、跨 Owner 拒绝、独立资源折叠 | “1101 项测试，所以合规满分” |
| 生命周期、故障、租约 | 15 | 请求丢失、过期、重启后会怎样？ | 受理不是完成，未知状态保持未知；原截止不被恢复偷偷延长 | 同构建故障、断线重试、旧回调、租约和预算回执 | 用一次正常运行代替故障覆盖 |
| 收回、保存与恢复 | 20 | 贡献者收回权与使用者工作如何兼顾？ | 展示停止确认、保存核验、新执行真实起点和资源不足等待 | 保存失败、无兼容资源、连续收回、预算耗尽与取消 | “有 checkpoint 按钮”就是完整能力 |
| 系统创新与价值 | 20 | 相比已有系统，你们究竟贡献什么？ | 说明我们围绕双方意图组织的端到端证据链，以及为避免虚报所做的取舍 | 机制的替代方案、代价、尚未验证的价值假设 | 把哈希、状态机、SQLite 或恢复本身说成首次发明 |
| 策略效果与复现 | 15 | 你们更好吗？是不是挑了有利例子？ | 明确 R=1.00，说明动作空间诊断与 Owner 伤害反例；新收益不虚报 | 配对输入、基线/消融、原始负结果；若另做窄比较须单独立项 | 将架构延迟改善当作调度策略提升 |
| 可观测性、工程与迁移 | 10 | 换个人能运行、定位和迁移吗？ | 一次决定能回到原始事件；证据可带走 | B 干净部署、新 UI 操作记录、环境锁、迁移/回退与 K8s 未实现边界 | 本地重放等于第三方复现，计划等于部署 |

前三项合计 55 分，是演示必须守住的地基。后三项 45 分决定作品是否超出普通完成作业，但不是“每增加一个功能多几分”。不预估自评分数，也不以开放项叙事掩盖硬门槛。

核心 API 缺失、可稳定复现的超卖/重复分配、基本贡献者回收失败，按题目会触发最高 59 分的限制。内部 CP4 规模/延迟门槛与上述官方硬门槛不是一回事；它们仍是我们自己承诺的质量要求，不能悄悄降低。

## 6. 哪些能力是基础，哪里可能形成真正的贡献

### 6.1 不把已有技术说成原创

Kueue 已有围绕配额、借用与优先级的抢占机制；HTCondor 支持应用主动保存、驱逐后的重启，以及 checkpoint 文件清单与校验。这些都是应当学习的既有能力，不能宣称我们首次解决了“能收回、能恢复、能验哈希”。参见 [Kueue 抢占文档](https://kueue.sigs.k8s.io/docs/concepts/preemption/)、[HTCondor 应用保存](https://htcondor.readthedocs.io/en/main/users-manual/self-checkpointing-applications.html)、[HTCondor 文件与校验清单](https://htcondor.readthedocs.io/en/25.0/admin-manual/file-and-cred-transfer.html)。这些资料用于厘清已有能力，不构成我们比它们更快或更安全的实验。

### 6.2 当前可以拿出来接受挑战的系统取舍

重点成果选择题目 **方向 B：贡献者友好型抢占与恢复**，以 **方向 F：可观测性与工程可信度** 支撑。不是同时宣称完成七个创新方向。基础恢复满足契约，而我们选择深入的设计问题是：多个异步模块分别返回“成功”时，用户能否错误地把它们理解为同一项工作已安全接续？

我们选择把“同一项工作的接续”作为跨多个模块的可检查对象，保留几个经常被界面混淆的事实：

```text
收回请求 → 保存报告 → 工件核验 → 原执行停止确认
                                 ↓
原租约与预算约束下等待资源 → 新执行实际应用保存点 → 结果 → 资源结算
```

这不是保证上述事实按一条直线全部成功。每一处都可能失败、取消或仍未知。关键是不能越过条件先显示成功：

| 不能合并的事实 | 合并后会造成的错误 | 我们要给出的证据 |
|---|---|---|
| 收到 ready / 工件可用 | 把空文件、错误来源或旧代次报告当成可恢复进度 | 摘要、格式、归属、工作/执行绑定与核验结果 |
| 可恢复 / 已恢复 | 新执行没有应用保存点，界面却说保住了计算 | 新执行起点与实际应用证据；同一工作与新 attempt |
| 发出停止 / 已停止 | 把仍在运行的执行与新占用同时放到资源上 | 停止确认；不能确认时保留隔离、不提前复用 |
| 工作完成 / 资源归还 | 输出有了，但租约仍持有资源 | 结果状态与租约状态分别读取 |
| 用户重试 / 新工作 | 响应丢失后重复登记、重复分配 | 稳定工作 ID、阶段回执与幂等核对 |

这种组合的价值需要用实际场景证明。它可以作为我们工程设计的重点，不足以单凭描述证明机制独创。

主讲可用一张三行小表替代技术栈：

| 容易误用的判据 | 当前实现额外检查及开发回归来源 | 付出的代价 |
|---|---|---|
| ready 报告即恢复许可 | 不存在的 URI 不能产生 verified；`tests/domain/test_cp2_adversarial.py::test_ready_report_does_not_fabricate_verified_artifact` | 工件验证与来源绑定，可能拒绝一次表面成功 |
| 发出停止即腾空 | 真实被冻结进程未观察退出前不能确认；`tests/executors/test_cpu_reference.py::test_stop_frozen_process_never_confirms_before_observed_exit` | 隔离与等待可能减少当时可用容量 |
| 恢复请求越多越可靠 | 32 个并发恢复只能建立一个新执行；`tests/concurrency/test_cp2_history.py::test_32_resume_requests_commit_only_one_replacement_generation` | 原子检查、幂等与预算约束，增加提交成本 |

这些用例在本轮 1101 项开发回归的收集清单中，原输出见 [工程证据](../../evidence/storage-architecture/engineering/pytest.txt)。它们是拒绝错误状态的针对性证据，不是与成熟平台的性能对照，也不是三个真实生产事故。最终候选应保留相关回归记录；不拿此表宣布新 UI 人验完成。它展示的是有代价的设计选择，效果与原创性仍须另证。

### 6.3 要从“可信原型”跨到“有说服力的创新”，还缺什么

最值得补的是一项小而严谨的因果比较：**在同一资源变化下，合法保存接续相较从零重启，究竟减少多少重复工作，增加多少保存与恢复代价？**

这个问题比继续对等价放置调分更接近题目矛盾。它也可能得到负结果，例如几乎没有有效进度或恢复成本过高时，保存不值得。

拟定而尚未执行的最小协议：

- 相同程序、输入、资源窗口、收回时刻、租约和预算；合法接续与合法从零恢复都遵守停止屏障和资源约束。
- 固定零可复用进度、中间进度、很晚中断三个条件；同时包含保存失败或无资源分支。不能只挑越晚越有利的中断点。
- 分开报告已核验且实际应用的步骤、保存后丢弃的尾部、重复计算步骤、保存/恢复耗时、等待时间、端到端完成/失败。所有失败进入分母。
- 用独立结果计算核验正确性；结果相同并不能单独证明复用，必须再核对新执行初始步数。
- 如有重复，只为估计宿主机时间噪声，不把同一输入的多次运行说成多个独立场景。不偷换成真实 GPU 训练收益，也不并入旧 R。
- 先记录预期可推翻条件、固定输入和预算，再运行一次最小矩阵。出现开销超过收益时原样保留，不为了路演重新挑参数。

这项比较是声称“机制带来实际收益”的 P1 证据门槛，不是可由视觉润色替代的附加项。顺序仍是先稳定候选，再冻结小矩阵并执行，不能为了路演收益无限扩展研究。没有完成，就把作品定位为可核验的系统设计与可靠性原型，不声称已有量化收益，也不预期靠讲述取得充分的策略效果分。若比较无收益，应报告何时不值得恢复；这同样不能冒领正收益。

## 7. R=1.00 应该如何讲

不能说“优化方法完全没有任何可能”，也不能说“只差一点调参”。已知原因是 P 被限制在 B2 已选工作的放置中，不能改变工作准入与服务顺序；统一工期使许多设备交换结果等价。790 次动作只改了 3 次，25 组总目标均相等。继续磨同一分数的边际价值低。

我们随后探索工作组合，发现局部平均值可以改善，却在有限供给窗口内牺牲宽工作 Owner。这个反例迫使我们拒绝把平均收益当作全面进步。两张卡、十秒窗口只有二十 GPU 秒，而三项工作总共要四十 GPU 秒：服务哪个人，是有代价的选择。

在台上只用二十秒说清研究判断，完整输入和推导放备份页。不要把负结果本身当创新，也不要靠诚信替代效果。可信的表述是：“这个版本没有展示策略加速；我们知道为什么，也知道下一步必须改变什么，而不是继续优化一个几乎不改变行动的评分。”详见 [原始诊断](../research/CP3_BOTTLENECK_AND_DIRECTION.md)。

## 8. 架构工作在路演中的位置

原结构每次普通写入都重复处理全量历史；本轮实体事务存储、活动索引和增量摘要针对这个结构性成本，保留原子账本和独立重放。它改善的是控制面的实现成本，和 P/B2 的完成时间目标是两个问题。

只有最终正式记录支持的数字才能进入主讲。目前普通写仍由 SQLite 串行，库存规模、活动工作、并发排队和磁盘同步都有成本。不能因为单请求探测变快，就说 32 并发 p95 已达标；也不能把 CPU 执行程序的耗时与 API 延迟混画一条曲线。

架构页采用“旧代价来源 → 本次变化 → 实测结果 → 未解决项”四格。若正式门槛仍未达，最后一格必须显示 NOT_MET，并保留完整结果。正式结果收录在 [本轮交付状态](../handoff/FINAL_PREPARATION.md)。不要在演示期间现场运行完整规模负载。

## 9. 展示组织：主线只允许一个中心

总览是开场的一眼：Alice 的真实工作正在运行，同时具有“我的工作”和“我的设备”两个经认证的入口。当前示例设备属于 Supplier；Alice 的设备列表为空就显示为空，不制造已经贡献设备的画面。同账户双能力是权限事实，不等于本场景中同账户已经拥有两类对象。随后点进工作，艺术层退去，视线落在同一条过程上。贡献者提出收回后，评委最关心的状态出现在原位，不要求他寻找“第三个模块”。

现场允许评委决定合法范围内的收回时机，以及被中断后继续还是取消。两个结局都必须如实：继续可能等待或失败；取消意味着不应被迟到回调复活。官方 3–5 分钟视频另录完整异常与恢复成功链，不能用取消结局代替恢复要求。

主讲不做六个工作区巡游，不放技术栈词云，不让页面上出现测试密钥、内网地址清单和 CP 检查表。关键边界用一句明示即可，详细协议放证据抽屉。工具应使评委容易追问，而不是用海量 JSON 阻止追问。

## 10. 执行顺序与停止条件

| 优先级 | 工作 | 责任 | 完成标志 | 不满足时 |
|---|---|---|---|---|
| P0 质量 | 合并 B UI、最终候选、原门槛复核、真实新环境部署与交叉操作 | A 后端/证据；B UI/新环境；双方人验 | 同构建、可追溯的实际记录，没有未关闭硬缺陷 | 不称最终发布，不用演讲润色代替修复 |
| P1 关键证明 | 一个同工作 ID 的完整真实 CPU 中断接续，独立核对起点和结果，浏览器下载原件 | A 准备核对；B 页面与操作；双方排练 | 从原件可复核；错误时页面不虚报 | 缩减主张，不能拼接不同工作伪造 |
| P1 路演 | 5 分钟核心稿、4 分 30 秒官方视频方案、现场分支与 Q&A | A/B 分工见执行手册 | 两次完整计时排练，第二位操作者能说明原因 | 删功能与术语，保留中心冲突和证据 |
| P1 价值证据 | 上述窄范围“接续/重启”因果比较；支撑实际收益主张的前提 | A 冻结协议与核对；B 复现和呈现 | 相同合法条件、完整成本和失败、负例保留 | 不声称已证明收益；降低作品主张，而非降低验收 |
| P2 可用性 | 新操作者是否把 ready 当恢复、受理当释放 | B 主导，A 观察 | 操作及协助记录，能定位误判原因 | 改信息表达，不继续加动画 |
| P3 修饰 | 总览艺术层、平滑转场、品牌微调 | B | 无动效可用，阅读不受影响，低配不卡顿 | 关闭或简化，不阻塞 P0/P1 |

不在最终冻结期间同时重写调度策略、扩大真实 GPU 范围和加入全新前端框架。真正的收尾是减少无法兑现的承诺，而不是减少验收质量。
