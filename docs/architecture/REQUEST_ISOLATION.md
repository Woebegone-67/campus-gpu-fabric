# 无故障请求的锁隔离补修

2026-11-15，继承实体存储候选 `c3fad1b`。第一轮正式负载的完整结果保留；此处不修改其源码、配置、运行目录或测量过程。

## 确认的结构问题

所有匹配公共操作的请求都会经过故障检查。此前即使没有配置注入规则，`take_fault` 仍先进入写事务；其调用发生在异步中间件的事件循环内。业务写线程持有 SQLite 写锁时，这个同步等待能阻塞其他请求分派和响应发送。它与业务必须串行维护账本的成本是两个问题，不能把两者统称为硬件上限。

本轮逻辑负载不启用 CPU 执行器、没有工作意图策略扫描，也没有注入故障，因此没有证据将此现象归因于这些后台任务。早期请求前缀延迟与只读静态路径分析保存在架构诊断目录；并不等于已经分离测得了每种等待的耗时。

## 修改与并发语义

故障检查整体在线程池执行，避免数据库等待阻塞事件循环。无规则、禁用规则或剩余次数为零时，从一致性只读快照返回，不取得写锁。这个快照是无注入判断的线性化点：在它之后并发配置的规则留给后续检查。

只读检查发现有效规则时，仍进入原写事务重新读取并原子消费。期间替换、禁用、重置或另一请求消费都必须以写事务内最新状态为准。不能依据前置快照消耗旧规则或重复使用一次规则。认证仍在故障消费之前；无效身份不消耗次数，也不被注入结果遮盖。

未关闭故障注入、未绕过权限、未降低 SQLite FULL、未修改公共 API 或正式负载门槛。业务写事务仍串行，线程池仍有界；本补修不保证消除所有排队或达到 200ms。

## 冻结的必要验证顺序

1. 真实 SQLite 写锁被另一线程持有期间，公共容量和实际任务详情读取仍能完成；覆盖无、禁用和耗尽规则。
2. 有效故障规则等待原子消费期间，另一个公共读取和无效身份拒绝仍能完成；释放写锁后只注入一次。
3. 两个独立 Kernel 并发读到一次有效规则，最终只消费一次；覆盖读后规则被替换、禁用、重置或消费的情况。
4. 对原行为做有界反证，确认新回归能抓住事件循环阻塞，而不是只测一个未经过公共中间件的探针。
5. 相关 HTTP、故障、并发检查与 Ruff。只重跑受影响范围，不重跑 125 组策略实验。
6. 第一轮正式尝试完成后，在同样 4 vCPU / 8 GiB 独立容器、新目录运行 **256 项工作** 的有界诊断，完整保留 1280 写请求与 32 次详情读取，仍用 32 并发、128 节点、全部历史与 FULL 持久化。它按原正式门槛必须标 NOT_MET，不能代替完整规模。
7. 仅当诊断已经支持原全规模与各操作 p95 门槛可行时，再进行一个冻结后的完整尝试。若仍存在显著串行/排队成本，则先定位剩余结构问题，保留未达，不反复启动明知不通过的完整负载。

有界新旧结果不是随机交错的同环境配对实验，不能宣称统计意义上的加速倍数。诊断即使在 p95 上较好，也不证明长历史、全部样本或最终 UI 已通过。源摘要、运行配置、失败样本与最后资源状态必须一同保存。
