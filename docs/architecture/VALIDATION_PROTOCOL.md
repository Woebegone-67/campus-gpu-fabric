# 实体存储改造的判定协议

实施期间冻结，首次新架构性能测量前写入。不是 CP4 通过声明。

## 先证明机制

1. 规范 JSON 单元和 Merkle 根由两个不同实现逐提交对照；独立端不导入生产存储或哈希树。校验原地修改、删除、空集合、未知字段、数值类型、混合 v1/v2 日志与旧库迁移。
2. 迁移必须保留旧日志原文；新单元、索引、树根、日志同一事务提交。拒绝、回滚和提交前后 SIGKILL 不能产生部分结果。
3. 固定活动对象与库存，将已完成历史从 0 增至 256、4096、10000 个无活动任务的历史实体。用于数量级检查的复制历史必须标为合成数据，不能声称经过这些任务的真实 HTTP 执行。断言普通写入实际解码/更新的实体数量不随这些历史线性增长；完整审计、重放、迁移和导出允许全量工作。
4. 只读查询保持同一 SQLite 快照；单任务详情和公共容量不能先加载全部私有历史。被阻塞的写事务不能占住 ASGI 事件循环。

## 有限诊断

固定 128 节点、每节点 8 张 A10 模拟库存，使用保留的原 CP4 256 个任务终态和全部原事件作为一次完整初值，不截断历史。与旧版同样执行 1 个准备生命周期、2 个无 profiler 的测量生命周期、3 次指定任务查询和 1 次空闲 worker tick。生命周期含申请、创建任务、实际延长租约、取消、归还五次写入。

报告每次操作原始时间与事务实际触及量。样本量只用于判断历史依赖是否解除，不给出统计显著、真实 GPU 加速或正式吞吐量结论。旧版已存诊断作为参考，明确不同代码日期和宿主机负载限制；若需要成对速度声明，必须另行同环境、同输入、交错顺序运行两版。

## 最终工程回归与正式负载

完成存储集成后执行一次完整工程测试（pytest、Ruff、契约生成一致性和前端构建）；仅失败修复或新增未覆盖风险才重跑相关项。不重复 125 组策略实验。

复杂度检查及工程回归满足后，冻结构建，使用 `tests/acceptance/cp4/LOAD_PROTOCOL.md` 原门槛运行一次完整负载：4 vCPU / 8 GiB、128 节点、1024 张卡、64 Owners、10000 任务、50000 写入、1250 查询、32 并发、1200 秒上限，普通请求 p95 < 200 ms。保持 WAL/FULL，保留慢请求、失败请求、全部历史与原始结果。

若完整负载失败，报告失败位置、原因和成本，不能把小样本或宿主机结果替代正式门槛。资源与状态正确性、独立重放、真人交叉操作、干净部署及最终录像分别验收。即使本次性能达标，尚未执行的真人与新 UI 项也不能自动 PASS。CP3 策略性能比 R=1.00 的冻结结论独立保留。
