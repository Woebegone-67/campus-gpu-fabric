# 资源局部化与写入准入：实施及验证协议

2026-11-15。基底 `b19acae`。这是在新计时证据支持下进行的结构改造，不改变 CP3 策略、冻结公共 API、正式负载或延迟标准。

## 为什么继续

原实体存储已消除终态历史被每写重复加载的成本，随后修复了无故障请求抢写锁与事件循环阻塞。但 256 工作诊断仍有秒级写尾延迟。一次成功的 64 工作、320 写请求阶段计时直接观察到：写锁获取 p95 约 3757ms，持锁服务平均约 26ms，库存构造占持锁业务处理时间约三分之二；最长等待期间大量后到事务先获得锁。计时器有开销，该结果用于定位，不当正式验收或精确容量定理。

因此同时处理两个结构：事务检查作用域与本进程写准入顺序。仅加 FIFO 不会提高单写者的服务能力，单改无关小函数也不能解决全池重建。完整初次失败与后续诊断材料保留，不回写旧记录。

## 不变的约束

- SQLite 的 BEGIN IMMEDIATE 仍是跨进程权威事务边界；WAL/FULL、每条命令回执、事件、状态根、幂等和原子账本保持。
- 不能只按命令名称豁免校验。续租末尾可能调度 Pending，取消可能自动释放，CPU 停止请求不能提前腾空，时钟与隔离记录会改变可用性。
- 比较事务实际执行和调度后的权威资源输入。未知、根替换、拓扑或旧 epoch 隔离复杂变动保守全量。普通占用变化只复核受影响节点，但包括这些节点的全部现存声明和物理父卡/切片关系。
- 加入启动与迁移后的全池资源语义基线；日志/树完整性不自动等于资源语义正确。离线完整资源折叠继续保留。
- builtin first-fit 可按原节点和设备顺序延迟求值，选中结果必须与原完整库存 first-fit 一致。外部决定继续按当前权威资源复查，不相信旧快照。
- FIFO 只声明其实际本进程作用域。跨进程仍由数据库决定顺序，不宣称全局公平；异常、拒绝、提交失败和回滚都必须释放准入。
- 不删除历史、不缩减节点/并发/样本、不排除慢请求、不关闭持久化、不放宽原 200ms p95。

## 验证顺序与边界

1. 资源变更接口覆盖原地嵌套变动、删除、根替换与未知结构；独立代理检查影响集合。
2. 必要场景：末尾再调度、自动结算、保存失败/成功、未确认停止、旧 epoch 隔离与重登记、MIG 父子冲突、节点状态、reset、时钟和拒绝不写。用全池参考派生/独立资源折叠对照，避免只复述新实现。
3. FIFO 实测先到写者不被本门内后到越过、异常不堵后续、读取不拿写准入、跨进程竞争仍不超卖。原等待线程取消或响应断开不能造成许可泄漏。
4. 运行影响范围的领域、存储、并发、HTTP 与 CPU 检查，统一执行一次工程回归；不重跑125组策略实验。测试失败必须修复并复验必要范围。
5. 源候选冻结后，先在 4 vCPU / 8 GiB 新容器按原 128 节点/64 Owner/32 并发执行 256 工作诊断，保留所有请求与最终状态。小规模永远不能给正式 PASS。
6. 仅当该诊断支持目标可行且没有语义缺陷时，再执行一次完整 10,000 工作/50,000 写/1,250 查询、1200 秒的正式尝试；使用同一冻结源码，复核全部样本和资源折叠。
7. 新 UI、另一真人干净部署、A/B 交叉操作和同构建实录独立完成。即使规模/延迟通过，也不自动宣布整体 CP4 通过或最终部署。

前一轮诊断工具首次未启动服务，实际零流程，单独保留 DIAGNOSTIC_FAILED；修复包装函数关键字冲突后唯一重试才得到64工作计时。工具退出码为0不是有效负载证明，必须同时核对实际完成数、HTTP错误与源身份。本轮继续遵循这一规则。
