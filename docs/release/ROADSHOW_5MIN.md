# 织算 五分钟路演

主线只有一条：当贡献者收回正在借出的设备时，一项工作怎样保住已经完成的计算，并在原来的约束下继续。让评委记住一次真实收回和一个可核对的计算结果。不要用六个页面巡游、技术栈词云或大量测试数量替代这个过程。

本稿对应仓库 55/45 评分标准。建议使用六个画面，实际讲述控制在 4 分 40 秒，最后 20 秒留给操作延迟。真实 CPU 参考执行、模拟 GPU 库存的范围在开始演示时说一次；成本对照图同样标明 CPU 参考负载。

## 可直接练习的讲稿

### 0:00–0:30

“请看这张正在被借用的设备。它属于实验室，下午主人要用，就必须能拿回来。但另一位同学的工作已经跑到一半。设备还回去，前面的计算怎么办？

我们做的织算，就是围绕这一次收回设计的校园算力池。”

### 0:30–1:00

“一个人既可以使用算力，也可以共享自己的设备。首页先告诉他哪些工作需要处理；打开工作台后，只处理任务和设备。

这里使用模拟 GPU 库存和真实 CPU 进程展示。程序会真实保存状态，再从保存点继续，最终文件可以下载检查。”

【打开已有运行中工作。不要在台上逐项填资源表单。】

### 1:00–2:10

“现在切到 Chen。他和 Alice 一样是普通用户，这两张 A10 卡由他共享。我们收回设备，提前通知三秒，自用十五秒。”

【确认收回，返回 Alice 工作并刷新。】

“这项工作收到通知后保存进度。保存文件经过核验，当前执行停止后才释放资源。现在没有兼容设备，所以先等。我们仍然保留同一项工作；等待期间不会凭空增加一次恢复。”

【点击恢复，等待设备回来，刷新。】

“看这里，第二次执行已经从保存点继续。原工作的名字、租约期限仍然在。使用者不用把一项中断拆成几份独立任务重新管理。”

【若在预定时间未进入接续，用下方故障分支，不反复点击。】

### 2:10–3:00

“我们的设计围绕一项稳定的工作展开。租约会中断，执行会换代，使用者仍能沿同一条记录找到中断原因、恢复起点和最终结果。贡献者也能确认设备何时真正停止使用。原租约截止和恢复预算继续有效。

背后有两个约束：确认旧进程退出，才允许复用资源；确认新进程真正加载保存点，才记为接续。最终结果可以下载，我们还用独立的矩阵计算核对它。”

【打开完成记录；展示结果和资源归还。若当前工作还未完成，切到明确标注为本次排练记录的备份，不把不同工作拼成同一次执行。】

### 3:00–4:05

“我们关掉了演示暂停，做了四种条件、三种策略的实际计算。

中期中断，从零重启重复五百零五万步；立即保存接续重复五万步，约二十毫秒确认停止。最简单的截止前保存策略，这次直接做完，零重复，但贡献者等了约五百五十八毫秒。

这是一项交换：更早还设备，还是多用通知期争取完成。保存失败的例子也保留了：立即接续四次完成三次，其他两种四次完成四次。我们没有发现复杂策略超过这个强基线，所以把计算损失和收回成本一起交给评委检查。”

### 4:05–4:20

“公共接口与同一账本承接这些操作；并发、超时和越权验证，以及本轮真实浏览器记录，都随版本交付。”

### 4:20–4:40

“现在，这项工作已经完成，设备也已归还。织算让贡献者看清收回是否兑现，让使用者看清进度是否真正延续。每一次状态变化，都能找到对应记录。”

## 成本图怎么做

只展示下面这个小表，不做装饰性仪表盘。每个数都对应本轮原始记录。步数是参考程序计算量，不是 GPU 训练步数，也不直接等于时间倍数。

| 中期中断策略 | 实际重复计算 | 通知到停止确认 | 全部四条件完成数 |
|---|---:|---:|---:|
| 从零重启 | 505 万步 | 10.1 毫秒 | 4/4 |
| 立即保存接续 | 5 万步 | 19.6 毫秒 | 3/4 |
| 固定截止前保存或完成 | 0 步 | 557.9 毫秒 | 4/4 |

中期行展示一次实际配对观察；最后一列包含零、中期、晚期、保存失败四种条件。通知到停止确认是执行器测量，不等于真实 GPU 物理归还延迟。完整平台链另有 Kernel + Driver 验证。晚期的重复计算分别为 905 万、5 万、0 步，留到备份材料。

图旁保留保存失败条件，不把成功子集当作整体胜出。第三种策略的完整逐例成本及贡献者等待，读取 `../research/FINAL_LOSS_ACCOUNTING.md`，不要隐藏负例。强基线的保存失败例没有触发保存，因此它的完成不能称为“抗住保存故障”。

不要在标题放“101 倍提速”“性能提升 99%”。本表比较重复计算步骤；CPU 时间、总耗时、贡献者等待分别报告。旧 P/B2 的 1.00 仍原样保留在研究历史和备份问答。

## 现场操作预案

提前准备三个独立浏览器配置文件或不同浏览器，分别登录 Alice（`alice`）、Chen（`chen`）和管理员（`admin`），打开原工作、我的设备和管理页面。同一浏览器配置文件中的普通窗口共用会话，不用于多账户同时演示。Alice 和 Chen 都是普通用户，均可使用算力和共享设备；这次分别演示借用与收回。画面投影以 Alice 为主，只在提出收回时切 Chen。不显示密码。准备一项刚启动的工作，确认实际有 A10 租约；不要拿已完成工作假装正在运行。

收回设置为提前 3 秒、自用 15 秒，选择两张 A10；先实际排练一次。工作若在提交收回前已经完成，就重新准备一项并明确重来，不套用以前的收回记录。演示用程序可以有节奏暂停来让人看清过程，但量化成本实验已经关闭暂停，两者不能混为性能证据。

- 网络或页面异常：只点一次操作，查原工作；若超过 10 秒仍不能判断，切换本轮留存记录，口头说“这是此前留存的完整演示记录”。
- 无资源：展示等待本身，不用管理员暗中加卡；用已保存完成链讲结果校验。
- 保存失败：解释这次没有成功接续，确认停止与资源归还，切到成功记录说明差别。失败不是按计划演出的成功。
- 总时间到 4:30：跳过管理员页面，直接回到工作完成与资源归还，保留总结。

## 困难问题短答

**这不就是 checkpoint 吗？**
Checkpoint 是已有技术。我们深入的是校园临时共享场景里的一整段工作：从贡献者发起收回，到文件核验、停止确认、原约束下接续、结果和归还。贡献不应靠改名认定；请看实测保留的工作量、等待代价以及失败时的行为。

**为什么不直接选最简单的截止前保存？**
它是很强的基线，在这组短参考负载里表现好；但会占用更多通知期。立即保存更早让出资源。当前没有实测支持在相同条件下复杂机制继续获益，所以我们保留这个比较并停止无收益扩张。未来要改变的是有代表性的负载和约束，不是继续调一个没改变动作的分数。

**你们之前的性能比不是 1.00 吗？**
是。那组 P/B2 比的是已选工作内部的放置，统一工期下多数交换不改变结果。那条优化没有提升。这次比的是中断后的重复计算与收回成本，指标和输入不同，不能把两组数拼成一条提速曲线。

**CPU 参考程序能代表 GPU 训练吗？**
它验证真实进程保存、恢复、结果等价，不能代表 GPU 训练性能。真实训练还需要框架 checkpoint、GPU 执行器、存储/传输与真实 profile。冻结公共 API 和执行器边界为接入留下位置，当前不声称已经完成适配。

**贡献者收回时，进程卡死怎么办？**
停止未确认时不会把资源重复分给另一项任务，保持隔离并暴露问题。这避免账本假腾空；不代表能保证任何操作系统故障下都按时停止。正常路径和冻结进程路径分别验证。

**如果所有人都想优先恢复？**
过去投入不是无条件优先的理由。应根据可验证的剩余工作、可用容量和公平约束决定准入。我们此前发现提高平均值会牺牲宽工作用户的反例，因此没有把那项策略上线。

**最终版本是否已经完成所有规模承诺？**
本轮最终技术验收范围与记录见 `FINAL_ACCEPTANCE.md`。旧 CP4 大规模和延迟目标仍有未达项，不用本机 UI 通过替代它。这个版本按明确范围冻结，未来性能工作有原始证据和停止点。
