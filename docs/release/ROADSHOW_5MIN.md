# 织算：五分钟路演

**请评委记住的问题：设备主人要拿回卡时，怎样决定再算、保存，还是停止？**

主角是收回通知后的决策。现场过程证明它真的执行；配对结果说明什么情况下值得这样做。按仓库 [55/45 评分表](../../spec/official/challenge.md)组织，讲述控制在 4 分 40 秒，最后 20 秒留给操作延迟。六个画面足够，不巡游全部页面。

## 时间、画面和可直接练习的讲稿

### 0:00–0:35｜同一张卡，两个人的时间

画面：一项正在运行的工作，旁边是一张属于另一位同学的共享设备。

“实验室下午要用自己的 GPU，但另一位同学的计算还没结束。立即停，可能丢掉已经算好的结果；一直等，设备主人又拿不回卡。

我们要决定的是：有限的收回窗口里，还值得算多少，什么时候保存，以及什么时候必须停止。织算围绕这个问题，做了可执行、可核对的收回管理。”

### 0:35–1:20｜四种选择，一个明确约束

画面：先完成、立即保存、稍后保存、直接停止；下方是一条归还时间线。

“我们用当前实际进度、保守计算速度和保存成本，比较四种选择。快完成的工作，争取直接交付；保存便宜，就马上保存；主人愿意多等，可以先多算一段；如果重算比保存还便宜，允许从零重启的工作可以直接停止。

比较的代价是归还后还要计算的量，加保存重启开销，再加设备主人的等待。默认尽快归还，主人也可以主动选择尽量保留计算。

所有选择都先预留停止时间。预测错了也不能无限等待；停止未确认的设备会保持隔离。”

### 1:20–2:30｜现场收回，计划与实际分开看

画面：两个独立登录会话。Alice 的工作正在运行；Chen 在“我的设备”收回自己的卡。两人都是普通用户，都能使用和共享设备。

“现在 Chen 提出收回。这里使用模拟 GPU 库存和真实 CPU 执行：计算、保存、停止和恢复都会实际发生。

Alice 不必点击同意。页面自动出现提醒，这一行说明系统选择了什么。选择先完成时，页面先显示继续计算；实际发起保存以后，才显示保存倒计时。”

【展示本次真实出现的动作，不把“优先完成”写成固定台词。保持工作详情，观察自动更新。】

“倒计时结束不等于设备已经归还。执行器确认进程退出，设备主人才会看到收回完成；进程不配合，系统会升级停止。使用者一直不操作，也不会阻止收回。

这次决策的输入、四个候选和实际停止时间都保留下来。工作继续时仍是原来的工作，租约期限不会重置。”

【展开“技术详情 → 收回决策记录”，指一次输入、一次选择、一次实际时间，随后收起。保存点可用时点击恢复，让计算在后面的讲解中继续。】

### 2:30–3:50｜不止战胜粗暴重启

画面：强基线对照表，标题注明“参数化执行模型”；突出一条获益案例，保留不利条件。

“我们还比较了立即保存、固定最晚保存，以及‘能完成就完成，否则立即保存’。后者是很强的简单基线。

一个直观例子：工作只算了半秒，保存却要两秒。选择从零重启，设备在零点一秒后归还；强基线要等二点一秒。我们多付半秒计算，省下两秒保存，综合代价从二十三点八降到二十点三。

全部十四个条件都保留时，默认的尽快归还模式，平均代价比强基线下降约百分之零点四八；两例更好，十二例持平。偏向保留计算时，保存耗时低估会反过来造成损失，整体比强基线高约百分之一点三一，还有一次超时归还。

我们展示的创新，是把双方的取舍变成能执行、能解释、能被对照检验的决策。收益在哪、风险在哪，都能定位到具体条件。”

### 3:50–4:30｜可靠性承担这项选择

画面：三条简洁证据链，保留当前工作完成或停止的结果。

“支撑它的是同一套资源账本：重复申请不会多分卡，跨账户不能拿走别人的设备，租约和重启预算始终有效。

保存报告、文件核验和实际接续是三个独立事实；发出停止指令和确认停止也是两个事实。异常分支不会被一个绿色状态盖过去。

公共接口保持赛题规范。真实进程验证、冻结的模型对照和原始决策记录分别交付，评委可以从干净环境重放，也可以换合法输入检查我们的选择。”

### 4:30–4:40｜收束

“织算让临时共享拥有明确的归还安排：设备主人知道何时拿回，使用者知道哪些计算保住了，双方都能看见这次选择的依据和结果。”

### 4:40–5:00｜预留

停留在工作结果或决策时间线。没有操作延迟时，留出自然停顿，不临时加功能介绍。

## 主图中的数字

主图只比较“能完成则完成、否则立即保存”与自适应策略，其他三种对照放备份页。两种偏好分别比较，不混合不同权重。单位为等价计算秒，不是 GPU 吞吐提升。

| 收回偏好 | 强基线平均代价 | 自适应平均代价 | 自适应逐例表现 | 平均设备主等待：基线 → 自适应 | 超时归还：基线 → 自适应 |
|---|---:|---:|---|---:|---:|
| 尽快归还 | 67.1143 | 66.7929 | 2 更好、12 持平、0 更差 | 1.1643 → 0.9857 秒 | 0 → 0 |
| 尽量保留计算 | 66.2411 | 67.1116 | 7 更好、5 持平、2 更差 | 1.1643 → 3.2750 秒 | 0 → 1 |

每行各有 14 个固定条件，全部计入。主表允许保存失败后从零重启，最终完成均为 14/14；保存失败次数分别为：尽快归还 1 → 1，尽量保留计算 1 → 2。强制要求保存成功的工作另有控制案例，不能用主表的冷重启收益替它背书。完整结果见[收回机制对照](../research/RECLAIM_AWARE_RESULTS.md)和[原始报告](../../evidence/reclaim-aware-20261115/report.json)。

低进度案例用于说明原理，不能取代全量表。保存低估的不利例中，自适应丢弃了 34.7 等价计算秒，强基线为 0。推迟保存依赖成本估计，这个反例必须保留。CPU 实机链证明实施路径，参数模型研究条件变化，两类证据不合并成一个实测加速比。

## 排练与故障预案

使用独立浏览器配置文件或不同浏览器分别登录 Alice、Chen、管理员。普通窗口共享会话，不能当作多账户。无需导入身份文件，刷新保持登录；密码不出现在投影画面。

准备一项确实运行中的工作，确认所选 A10 属于 Chen。建议收回提前通知 15 秒、自用 15 秒，给预测、保存和停止留出可观察窗口；以本机排练为准。工作已完成就重新准备，不能把旧截图拼成当前运行。演示保存接续使用“保存点恢复”；讲解允许放弃低价值进度的策略，明确采用“尽力运行”。

现场只保留一次收回、一次决策查看、一次恢复。页面每两秒自动更新，不连点刷新。若显示“状态待更新”，检查连接；十秒内仍无法确认，就切换明确标注日期和工作 ID 的留存录屏，并说明是此前记录。

“停止未确认”意味着设备仍隔离；不能由管理员改成成功。保存失败就展示失败和归还。逻辑模拟实例不能靠现实等待推进，现场使用 CPU 实例。操作期间若工作提前自然完成，就展示实际完成，不能伪造中断。

## 备份问答

**这不是已有的 Checkpoint 吗？** 保存和恢复已有成熟实践。我们研究的是主人提出截止时间以后，怎样从四个动作中按双方代价作选择。Kueue 已有抢占，SkyPilot 已有故障恢复与保存点接续，因此不声称发明 Checkpoint，也不声称全球首创。我们的主张限于校园临时共享中的具体机制及可审计实现。[Kueue 官方说明](https://kueue.sigs.k8s.io/docs/concepts/preemption/)、[SkyPilot 官方说明](https://docs.skypilot.ai/en/latest/examples/managed-jobs.html)。

**只有 0.48%，为什么值得做？** 全量平均增益很小，不能包装成性能突破。它定位了强简单基线漏掉的具体情形：保存比重算更贵时，应允许提前归还。我们把这项有条件的选择落实到产品，也保留失败条件；下一步应针对估计误差，而非追逐小数点。

**是不是绝对准时拿到卡？** 系统预留停止时间并主动停止，不依赖借用者同意。宿主卡死或停止耗时超过估计仍可能晚归还；这时记录超时并隔离，绝不会把未停止的进程说成可用资源。

**能恢复所有 AI 程序吗？** 当前真实执行使用受控 CPU 参考程序。任意训练任务须接入自身保存/恢复协议并核验文件和执行代次。本轮没有实现真实 GPU 执行、共享保存带宽优化或风险感知放置。
