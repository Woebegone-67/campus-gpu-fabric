# 面向贡献者收回的自适应执行安排

日期：2026-11-15。对应赛题方向 B“贡献者友好型抢占与任务恢复”。实现入口是生产规划器 `src/campus_fabric/policies/reclaim.py`，实际执行由生命周期内核与 CPU 执行器承接；扩展接口不改变冻结的公共 API。

## 1 问题和核心主张

已借出的设备收到收回通知后，剩余窗口既有价值，也有成本。多算一会儿可能直接完成，或让归还后的剩余计算更少；但保存会阻塞计算，设备主人还要承担等待。保存本身昂贵、进度很少时，保存甚至比从头重算更不划算。

因此系统在同一组可观察信息下比较四个动作：先完成、立即保存、推迟保存、停止。先保证时间与恢复语义约束，再最小化“归还后剩余计算 + 保存和重启开销 + 加权设备主等待”。选定动作会实际驱动执行器，决策输入、候选以及实际时间可持续审计。

这是一项面向具体收回场景的成本与可行性选择机制，不是新的通用调度最优性定理。它不声称发明 Checkpoint 或抢占：Kueue 已有优先级、配额与公平共享相关抢占；SkyPilot 已支持故障恢复及应用保存点接续。我们的比较对象是收回窗口内的四种动作及其双边成本，不是以完整平台替代这些系统。[Kueue 官方文档](https://kueue.sigs.k8s.io/docs/concepts/preemption/)、[SkyPilot 官方文档](https://docs.skypilot.ai/en/latest/examples/managed-jobs.html)。

这里“处理权衡”指建立并执行一个明确、可反驳的决策规则；不等于证明对所有负载都优于简单基线。本轮强基线下平均增益小，另一偏好在压力条件下更差，这些结果保留。

## 3 输入来自哪里

规划器只接收通知时可观察的进度、总步数、吞吐区间、保存与重启成本估计、停止预留、主人截止和任务保存期限。真实执行器读取带签名的进度文件，校验任务、执行代次、单调时间与步数范围，再交给内核。普通 HTTP 用户不能提交“可信进度”来影响算法。

CPU 当前保留最近八个进度样本，使用有效相邻间隔估计速度；保守下界为最小观测速度的 0.75 倍，上界为最大观测速度的 1.25 倍。至少两个有效间隔才形成速度区间。规划器要求可信数据在一秒内有效。缺少、过期或不足的数据不触发积极延后，回退到立即保存；窗口不足则停止。

保存成本上界由参考执行器的观测间隔保守放大，停止预留包含 TERM 到 KILL 的升级等待及驱动轮询余量。这些都是运行估计，不是可证明的硬实时上界。当前小状态 CPU 文件不能标定真实模型数 GB 的保存时间，参数研究中的昂贵保存条件属于敏感性探索。

## 4 约束与目标函数

记当前时刻为 t，主人截止为 D，任务保存截止为 C，预计停止确认耗时为 s，预计保存成本为 c。执行停止边界为：

`H = max(t, min(C, D - s))`

最晚开始保存时刻为：

`T_save = H - c - 0.1 秒报告余量`

任务预计剩余计算 R 使用剩余步数除以速度下界。四个候选的估计成本如下；所有时长统一为秒。

| 动作 | 可行性条件 | 归还后剩余计算 | 保存/重启开销 | 设备主等待 |
|---|---|---:|---:|---:|
| 直接停止 | 工作允许从零重启；紧急收回时仍可强制停止但不能称成功恢复 | 全部计算 | 重启成本 | s |
| 立即保存 | 当前开始保存仍赶得上 H | R | c + 重启成本 | c + s |
| 稍后保存 | 可信估计；T_save 晚于当前，且不能先完成 | max(0, R - 延后时长) | c + 重启成本 | 延后时长 + c + s |
| 优先完成 | 保守 R 能在预留保存窗口之前完成 | 0 | 0 | R + s |

在可行候选中最小化：

`J = 归还后剩余计算 + 保存/重启开销 + λ × 设备主等待`

默认“尽快归还”使用 λ=1；“尽量保留计算”由主人主动选择，使用 λ=0.25。相同分数优先等待更短的动作。权重公开固定，不根据实验结果调权。

目标把完成前继续使用设备的成本计入主人的等待，把归还以后借用者仍要完成的计算单列。它不是总计算量、总作业完成时间、能源、公平福利或 GPU 吞吐。减少 J 不能直接叫作“整体性能提高”，更不能自动称为双方每个指标都改善。

“保存点恢复”是硬语义：没有可用保存点就不能把冷重启说成成功接续。生产规划器对这种工作禁用经济性放弃保存；窗口不足仍以收回为先，工作可能失败。允许从零重启的“尽力运行”才适用低进度、高保存成本下直接停止的收益。

## 5 从计划到实际执行

收到合法收回请求后，内核锁定受影响租约，进入抢占过程，并保存规划器输入、所有候选、所选动作、理由和计划时刻。设备归属由服务器校验。收回不需要借用者点击同意，也不受其未主动释放影响。

`finish_first` 和 `save_at` 在保存前继续计算；达到计划时刻还未结束，就请求保存。优先完成没有按预测完成时保留保存兜底。达到 H 后请求停止。收到真实完成时立即归还，不为等待原计划而继续占用。

执行器先请求进程退出，必要时升级终止。只有确认进程退出后才解除占用；无法确认时保持隔离并暴露失败，不能先释放账本再让旧进程继续运行。签名保存报告、文件核验、下一次执行实际加载保存点分别记录。连续收回不能放宽此前更早的停止边界；恢复继续使用原工作和原租约期限。

“保存计划”与“保存事实”在界面中分开。全局提醒和工作详情显示当前阶段；计划等待时显示继续计算或开始保存前的时间，实际保存后才显示保存剩余。保存剩余使用实际 H，主人收回剩余使用 D，两者不同是正常的。超过数据新鲜度则停止推算并提示状态待更新。数字归零只等待服务端确认。

当前状态通过 `/x/v1/recalls` 按账户投影；完整历史通过 `/x/v1/work-intents/{id}/reclaim-decisions` 读取，放在“技术详情 → 收回决策记录”。完成和恢复后仍能追溯原输入、候选和实际保存/停止时间。设备主人只看到自己设备的收回进度，不获知借用者私有工作内容。

## 6 对照设计和当前结论

对照使用 14 个固定条件、5 种策略、2 档偏好。四个基线分别是从零重启、立即保存、固定最晚安全保存，以及“能完成则完成、否则立即保存”。固定最晚保存并非粗暴定时器：它拿到相同成本估计和停止预留；完成优先基线也使用相同保守剩余时间。

自适应组直接调用生产规划器。协议区分可见的 observed 输入与只供结果计算器使用的 actual 参数；后者不能进入在线决策。实际模型让保存阻塞计算，成功保存才保留进度；保存失败、重复收回、速度下降、保存或停止低估都保留在分母里。主表允许一次冷重启恢复，并单列必须保存成功的控制案例。

| 偏好 | 强基线 J | 自适应 J | 全部 14 条件表现 | 主人平均等待：基线 → 自适应 | 晚归还次数 |
|---|---:|---:|---|---:|---:|
| 尽快归还 | 67.1143 | 66.7929 | 2 赢、12 平、0 输 | 1.1643 → 0.9857 | 0 → 0 |
| 尽量保留计算 | 66.2411 | 67.1116 | 7 赢、5 平、2 输 | 1.1643 → 3.2750 | 0 → 1 |

默认偏好相对强基线全量均值降低约 0.48%，不能作为大幅性能突破。明确的增益集中在零/低进度且保存昂贵的可冷重启工作。更偏向保留计算时，正常条件可以获益，但保存低估造成的损失使全量均值反而高约 1.31%。因此后者保持主动选择，不作为默认策略，不能把正常条件筛出来宣称全面胜出。

低进度例中，重算 0.5 秒换来少做 2 秒保存，设备主等待由 2.1 秒降到 0.1 秒，J 从 23.8 降到 20.3。保存低估例中，延后保存丢弃 34.7 等价计算秒，而强基线为 0。这两个例子共同界定机制价值：要比较保存与重算成本，也必须估计保存的不确定性。

数据来源与逐例反事实见 [RECLAIM_AWARE_RESULTS.md](RECLAIM_AWARE_RESULTS.md)、[冻结协议](../../evidence/reclaim-aware-20261115/PROTOCOL.md)及[原始报告](../../evidence/reclaim-aware-20261115/report.json)。管理页面“收回策略对照”按偏好分表，并提供报告、协议下载；规划器哈希不匹配时标为历史策略版本。

## 7 证据分层与边界

| 层次 | 能支持的结论 | 不能替代什么 |
|---|---|---|
| 参数化配对模型 | 规定输入与成本假设下，动作选择的条件收益和失败边界 | 真实 GPU 训练效果、校园负载分布或统计普遍性 |
| 真实 CPU 产品链 | 规划真正驱动保存/停止，未操作的借用者不能卡住收回，事件与状态对应 | 大模型保存耗时、跨机带宽或 GPU 物理回收测量 |
| 公共接口和边界测试 | 覆盖项内的账本、隔离、幂等、租约与异常语义 | 隐藏测试成绩、另一真人干净部署或整体无 bug |

本轮浏览器记录位于 `evidence/reclaim-live-20261115/`。正常保存与冻结进程后强制停止分别记录，不把一个成功例替代另一个失败路径。验收范围以该目录的实际回执为准。

仍未实现的方向包括：任意 GPU 训练保存适配、跨机保存与带宽争用、风险感知放置、在线估计不确定性校准。当前机制只处理通知后的单任务选择，不能在路演中把这些扩展说成已完成。

停止确认仍依赖宿主与执行器的可用性。时间预留不足或系统异常可能导致晚归还；系统保持隔离并记录实际延迟，不承诺绝对硬实时。安全性与准时性分别报告。

## 8 展示与后续投入原则

五分钟先让评委看到双方冲突，再讲动作选择，接着证明真正在执行，最后展示强基线和反例。不要把已经实现的基础能力包装成研究突破，也不要用大量模块或测试数量掩盖收益很小。

下一步真正值得研究的是保存成本估计失准的识别与保守安排，前提是有独立的新负载和可信测量。本轮冻结后不继续调权、不删除不利条件、不围绕已有 14 条件做追分。当前可主张的是一个有条件收益、可执行且可审计的场景机制。
