# 最终损失核算：保存接续有价值，但强简单基线已覆盖当前额外机会

后续进展：本页保留当时 12 条真实 CPU 对照及其结论。此后新增的通知期自适应动作决策与参数化对照见 [面向贡献者收回权的自适应计算管理](RECLAIM_AWARE_RESULTS.md)；两项研究的负载、指标和证据层级不同，不覆盖本页原始结果。

2026-11-15。本轮完成 12 个真实 CPU 执行对照、1 条真实 Kernel/Driver 接续链和一次只读原件复算；没有重跑 CP3 的 125 条轨迹，没有修改业务内核。本报告不宣布 CP4 通过，不代表 GPU 训练性能。

**结论：中、晚期已验证保存接续明显减少重复计算；零进度没有收益，保存失败也不能消失在分母里。当前小状态 CPU 程序没有证明比正确简单结算策略更好的新算法。** 下一步应研究真实保存瓶颈，而不是继续优化本例的评分或参数。

## 1. 实际执行了什么

跑前协议与增补均先于实测保存，见 [PROTOCOL.md](../../evidence/release-20261115/research/PROTOCOL.md)。参数固定：同一整数程序、seed 17、1,000 万步、每批 5 万步，`batch_pause_seconds=0`；1 秒收回通知，40 秒统一观察窗，最多一次恢复。没有人工放慢计算。研究进程调用未修改的 `CpuReferenceExecutor` 和真实 worker，计时包装仅测量真实计算与文件写入。

三个研究臂分别是：

- **立即保存接续**：收到通知即保存，经核验后停止，确认进程结束后从工件起点恢复。
- **合法冷启动**：通知后直接停止，确认结束后以同一工作/任务身份的新代次从零开始。它是研究执行器级策略；当前产品 API 没有“已有有效工件但用户强制冷启动”的入口。
- **固定截止结算强基线**：继续运行至通知截止前 100ms；此前自然完成就交付，否则保存并停止，截止时仍未保存则要求停止。该臂实际运行，不是模型推演。

代码字段仍称第三臂 `finish_fits`，但**实际执行不依赖剩余时间预测**。因果预测另外记录；即使中期预测不适合直接完成，程序也可能在固定保存边界之前自然结束。不能把这解释为预测算法胜出。原始 JSON 中预测字段的旧 `scope` 文案只描述诊断预测，不否认第三臂实际执行；[独立复算说明](../../evidence/release-20261115/research/audit-01.json) 明确记录这一澄清，原件未改写。

12 条研究臂使用立即重新授权来隔离计算损失，**未包含贡献者真实自用时段和再次等待可用资源**。另用真实 Kernel/Driver 链验证实际通知、资源释放、无可用资源等待、原租约恢复和自动归还。两类证据分开报告。

## 2. 返工账：只有实际接续才兑现保存价值

每个程序需要 1,000 万步。下表的重复计算是“已完成工作总执行步数减所需步数”；没有把中断丢弃尾部与后续重复步骤再加一次。

| 中断位置 | 方法 | 第一代最终步骤 | 第二代起点 | 总执行步骤 | 重复步骤 |
|---|---|---:|---:|---:|---:|
| 零进度 | 立即保存接续 | 50,000 | **0** | 10,050,000 | 50,000 |
| 零进度 | 冷启动 | 0 | 0 | 10,000,000 | 0 |
| 中期 | 立即保存接续 | 5,100,000 | **5,050,000** | 10,050,000 | 50,000 |
| 中期 | 冷启动 | 5,050,000 | 0 | 15,050,000 | 5,050,000 |
| 晚期 | 立即保存接续 | 9,100,000 | **9,050,000** | 10,050,000 | 50,000 |
| 晚期 | 冷启动 | 9,050,000 | 0 | 19,050,000 | 9,050,000 |

中期与晚期分别少执行 500 万和 900 万步；这不是把“905 万步已保存”直接当作“905 万步已节省”。保存后到停止命令抵达之间，第一代仍多算了一批 5 万步，正是本轮保留的尾部损失。零进度工件恢复起点确实为 0，因此没有复用价值，反而增加了一批返工和流程成本。

所有导出的 checkpoint/result 均用独立矩阵 oracle 核对完整整数结果；逐代起点又与 worker 的 started 记录一致。四次已保存工件的复制件被损坏后，真实执行器均拒绝恢复，新增执行代次为零。没有用生产 `advance()` 来生成独立期望值。

## 3. 时间和成本：不能只展示使用者更快

单位为秒，每格均为本轮单次观测；没有用它们估计总体加速比或统计显著性。

| 场景 | 立即保存接续：端到端 / 纯计算 CPU | 冷启动：端到端 / 纯计算 CPU | 固定截止结算：端到端 / 纯计算 CPU |
|---|---:|---:|---:|
| 零进度 | 1.322 / 0.970 | 1.203 / 0.940 | 1.274 / 0.985 |
| 中期 | 1.225 / 0.975 | 1.731 / 1.414 | 1.140 / 0.953 |
| 晚期 | 1.248 / 0.993 | 2.349 / 1.978 | 1.174 / 0.975 |
| 保存写入失败 | **失败** / 0.499 | 1.790 / 1.461 | 1.207 / 1.023 |

本轮 checkpoint 原始文件仅 587–611 字节，实际写入约 0.21–0.35ms，核验约 0.18–0.28ms；恢复/冷启动从 dispatch 到 started 约 44–62ms。当前状态太小，**保存 IO 不是本例的实测主要瓶颈**。

下表为通知到实际进程结束确认，单位 ms；这些是执行器级观测，不冒充 GPU 账本时间。

| 场景 | 立即保存接续 | 冷启动 | 固定截止结算 |
|---|---:|---:|---:|
| 零进度 | 59.38 | 50.23 | **920.88** |
| 中期 | 19.57 | 10.06 | **557.86** |
| 晚期 | 19.93 | 11.86 | **118.37** |
| 保存写入失败 | 13.57 | 10.96 | **591.66** |

强基线在中期比立即保存多占用约 **538ms** 的通知窗口，在晚期多占用约 **98ms**。它使用了贡献者允许的额外时间，不能宣传为无成本优势。零进度场景还使用约 921ms 才完成停止，随后保留 745 万步恢复；这不能与立即保存的零进度工件混为同一事实。

12 条运行均未观测到超过 1 秒通知截止；**100ms 提前量并不是经证明的最坏保存/停止上界**。实际部署仍须保留停止屏障、未知进程隔离、故障及边界测试。

`worker_occupied_wall_seconds` 这个原始字段只包含 wrapper 内部 worker 运行，不含解释器/模块加载和最后计量落盘退出，不能当完整资源占用。复算补充了 dispatch 到每代退出确认的保守执行槽占用：中期接续/冷启动为 1.223/1.730 秒，晚期为 1.247/2.348 秒。纯计算 CPU 来自 `process_time_ns` 包裹真实计算；不是整机 CPU 使用率、能耗或 GPU 利用率。

## 4. 失败保留以后，结论必须改变

故障在 checkpoint 文件写入前真实抛出 OSError，worker 因此退出；这是明确注入的保存故障，不冒充自然磁盘故障。立即保存接续安全失败，不能伪造保存成功。冷启动不调用保存；强基线在故障场景中先自然完成，**未触发那次保存写入**，因此不能说它抵抗了保存失败。

| 方法 | 完成 / 全部场景 | 失败 | 全分母 F（秒） |
|---|---:|---:|---:|
| 立即保存接续 | 3 / 4 | 1 | **43.795** |
| 冷启动 | 4 / 4 | 0 | 7.073 |
| 固定截止结算 | 4 / 4 | 0 | 4.795 |

F 从初次 dispatch 起算，失败/未完成计至预先固定 H=40 秒。这个小型故障组成不是校园真实故障分布；不能将 F 大小外推为全平台排名，也不能排除故障行后宣称保存策略全面更好。表明的只是：保存价值有成立条件，完成分母与失败处置比单独统计“保留多少步骤”重要。

## 5. 真实产品链核验

[kernel-path.json](../../evidence/release-20261115/research/run-01/kernel-path.json) 使用真实 Kernel、单调时钟、CpuDriver 和资源账本，正常调用贡献者收回与 Owner 恢复，未使用逻辑时间快进：

- 同一工作 `loss-product-path`、同一租约和任务，执行从第 1 代变为第 2 代；重启预算只消耗一次。
- 保存并实际应用 **5,250,000 步**，最终完整结果与独立 oracle 一致。
- 通知到观察到账本释放 **61.90ms**；此时真实进程已退出确认。
- Owner 授权后仍等待被收回资源重新可用；下一代启动距第一代结束约 **2.004 秒**，没有把等待假称为已接续。
- 原租约到期仍为 30 秒；最终完成并自动释放。

这一条证明产品可以执行相应链路；不能替代所有并发、隐藏故障或完整 CP4 验收。

## 6. 强基线裁决与下一步

**本轮不成立的新主张：**没有证明预测驱动的新保存算法优于固定截止结算。当前所谓候选若采用同样的等待/保存边界，就与该强基线等价，不应再跑一份相同结果并命名创新。原 CP3 放置 P/B2 的 R=1.00 原样保留，本轮不回填其成绩。

可立即交付的设计价值是双向承诺的可执行闭环：贡献者设定回收界限，使用者的进度有可核验起点，停止确认后才重新利用资源，实际应用以后才计入保存价值。将固定截止结算接入产品会是有依据的设计改进；它不是 checkpoint 发明或普适新算法。本次只研究，没有将第三臂接入业务内核。

**值得下一步探索的最小新方向：同时收回时的保存带宽分配。** 本题真正尚未被本例覆盖的是多个有状态任务争用保存通道；需要先用一个真实 CPU 训练微负载，保存模型、优化器与 RNG 状态，标定有效状态大小和保存/恢复成本，而不是写无用大文件或加入 sleep。只用 2–3 项任务、小量固定场景，比较：

1. 固定提前量 + 能完成则完成；
2. 最早截止先保存（EDF）；
3. 按可保留进度/实测 IO 成本的简单贪心；
4. 若前三者确有可证冲突，再研究有 Owner 服务底线的联合选择。

所有方法使用相同因果可见数据、同一真实保存带宽、停止界限与任务分母。若保存成本或竞争根本不构成损失，则不实现联合机制；若为了平均收益使某 Owner 完全失去服务，则拒绝推广。它改变的是有限收回窗口内能留下多少有效工作，而非重复调整等价 placement。尚未运行，不能提前填收益。

## 7. UI 展示与可公开表述

真实 UI 演示用现有产品路径：创建具名工作 → 中途由贡献者收回 → 查看已核验保存 → 原工作选择继续 → 等待资源 → 新代次接续 → 下载完整结果。页面数值必须来自该现场工作，不能把本实验步骤贴到另一项工作上。当前普通 UI 不包含第三臂，不现场冒充已上线。

台上可说：“在这次固定 CPU 程序的中期中断实验里，冷启动重复算了 505 万步，接续只重复 5 万步；原工作从核验过的 505 万步继续。零进度没有收益，保存失败也会失败。”随后展示真实 UI 的本次起点与结果作为另一条证据。

若追问最佳策略，可说：“简单地利用允许的通知窗口继续完成，本例已经更好；代价是贡献者多等。我们没有把这个简单策略包装成新算法。”不可公开声称真实 GPU 加速、总体吞吐提升、全局最优或完整 CP4 通过。
